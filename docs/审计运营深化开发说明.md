# 审计运营深化开发说明

## 1. 目标与安全边界

本模块基于 Gin + GORM + MySQL，提供审计归档、保留期清理、接收回执、平台侧死信运营以及其他 Go 系统可复用的 Outbox 示例。不使用 Redis，也不提供按单条审计事件任意删除的接口。

安全边界：

1. 审计事件正文、死信原始 Payload、应用 Token、客户端密钥和上游原始错误正文不得返回浏览器或进入普通日志；
2. 归档文件只能由受控 Worker 写入 `FILE_STORAGE_ROOT` 下的专用目录，数据库仅保存相对路径、摘要和清单；
3. 清理只能基于已完成归档清单执行，不能按事件 ID 或任意查询条件直接删除；
4. 死信重放必须重新校验载荷并调用现有审计接收服务，不能绕过应用、环境、租户和幂等约束；
5. 其他系统的 Outbox 属于其本地事务边界，平台不能远程操作业务系统的 Outbox 表。

## 2. 已实现能力

### 2.1 接收与回执

- 应用 Bearer Token + `audit.ingest` Scope 的单条、批量审计接收；
- `(application_id, event_id)` 幂等去重；
- `audit_ingestion_receipt` 持久化批次运输回执；
- 回执按租户、应用、环境、状态、Request ID、Correlation ID 和时间范围查询；
- 查询结果只返回运输与计数信息，不返回事件正文。

### 2.2 归档与保留期清理

- `RetentionService` 创建和分页查询归档/清理任务；
- `ArchiveWriter` 生成 gzip NDJSON，采用临时文件原子发布、SHA-256 和受控相对路径；
- 归档任务保存 `archive_id`、候选数量、实际处理数量和结果；
- 单任务最多归档 5,000 条，超过限制安全失败，不把部分结果标记为完成；
- 清理任务只删除已进入归档清单的在线审计行；
- `RetentionWorker` 使用 MySQL 行锁、`SKIP LOCKED` 和陈旧锁恢复，支持多实例安全领取；
- Worker 已与审计导出 Worker 一起接入 `cmd/worker` 生命周期。

### 2.3 死信运营

- 平台侧死信分页查询和状态查询；
- 单条重放和最多 100 条批量重放；
- 单条失败不阻塞同批其他死信；
- 重放失败保留待处理状态、原子递增尝试次数并写入受控失败码；
- 重放结果接口不返回原始 Payload 和内部错误正文；
- 单条、批量重放和保留期治理操作由权限与 MFA 二次验证保护。

### 2.4 其他系统 Outbox 示例

示例位置：

```text
backend/internal/platform/audit/integrationexample/
├── outbox.go
├── http_sender.go
└── outbox_test.go
```

标准做法是在业务 GORM 事务中同时写业务数据和本地 Outbox 行，由业务系统 Worker 使用短期应用 Bearer Token 调用 `/api/v1/integration/audit/events:batch`。`ACCEPTED` 和 `DUPLICATE` 都可标记本地投递完成；不可用或拒绝时由业务系统按本地策略重试并最终进入其自身死信。

## 3. 已注册管理接口

以下均为用户管理端接口，使用 HttpOnly 会话和租户上下文，不是应用审计上报接口。

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| `GET` | `/api/v1/audit/ingestion-receipts` | `platform:audit:ingestion-receipt:view` |
| `GET` | `/api/v1/audit/retention-tasks` | `platform:audit:retention:manage` |
| `POST` | `/api/v1/audit/retention-tasks` | `platform:audit:retention:manage` + MFA 二次验证 |
| `GET` | `/api/v1/audit/dead-letters` | `platform:audit:dead-letter:view` |
| `POST` | `/api/v1/audit/dead-letters/{dead_letter_id}:replay` | `platform:audit:dead-letter:replay` + MFA 二次验证 |
| `POST` | `/api/v1/audit/dead-letters:replay` | `platform:audit:dead-letter:replay` + MFA 二次验证 |

表结构由 `000032_create_audit_operations.sql` 创建，资源和权限由 `000034_seed_platform_operations_permissions.sql` 初始化，OpenAPI 已同步。

## 4. 组合根、Worker 与前端

- API 组合根已创建回执、保留任务、死信服务和 `OperationsHandler`；
- 治理审计适配器调用现有审计接收服务，并使用配置中的平台应用/环境编码；
- `cmd/worker` 已并行运行审计导出 Worker 和审计保留 Worker；
- `AuditOperationsModule.vue` 已挂载到 `PlatformConsoleView.vue` 的审计区域；
- 前端不展示死信 Payload、归档物理路径或应用凭据。

## 5. 当前限制与后续验收

- 本地归档目录在多实例部署中需要共享文件系统、单 Worker 约束或明确的实例归属策略；
- 超过 5,000 条的单任务归档需要先设计分页、多文件清单协议后再放宽；
- 仍需在真实 MySQL 环境完成多实例并发领取、陈旧锁恢复、归档摘要和清理清单一致性的端到端验收；
- 仍需手工确认 API 和日志中不出现死信 Payload、Token、密钥和上游原始错误。
