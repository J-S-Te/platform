## 2. 原始需求中的关键调整项

| 原始表述 | 调整后的实施要求 | 原因 |
|---|---|---|
| 合同系统自行登录、签发 JWT | 合同系统作为 OIDC 客户端，使用 Code + PKCE；后端本地验签 | 统一身份与标准协议 |
| 前端 SHA-256 密码并与明文一起提交 | 不在业务应用传输或管理平台密码；全程 HTTPS，密码策略由 IAM 执行 | 避免自定义密码协议和重复凭证处理 |
| 用户表直接保存 `dingtalk_unionid` | 使用 `iam_external_identity` | 支持多身份提供方并保持账号模型清晰 |
| 用户物理删除 | 禁用/离职/保留历史，确保合同与审计可追溯 | 审计、外键引用和合规保留 |
| `contract.create` 等权限编码 | `contract:contract:create` 等三段式编码 | 按应用命名空间避免跨系统冲突 |
| 业务模块写审计日志表 | 本地 Outbox + 平台审计 API/SDK 幂等上报 | 避免跨模块直连与丢失审计 |
| 审计日志兼作程序日志 | 审计与运行日志/Trace/Metric 分离 | 满足安全和可观测性边界 |

## 3. 覆盖性结论

- 原始 24 个功能编号均已映射到一个拆分后的领域文件。
- 原始功能细节均以“原始需求摘录（完整保留）”的形式保留在对应文件。
- 基础能力平台文档中原始需求未覆盖的接入约束（Application 注册、OAuth Client、Token 本地验签、Outbox 审计、数据范围、配置版本、OTel）已作为实施基线补充。
