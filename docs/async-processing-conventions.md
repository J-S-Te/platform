# 异步处理使用边界

本文记录当前系统的异步模式选择规则。它是跨仓库稳定协议，不是要求各子系统导入同一个业务实现包；每个子系统应在自己的代码和数据库边界内实现相同约束，以便后续独立剥离和部署。

## 模式选择

| 模式 | 适用场景 | 不适用场景 |
| --- | --- | --- |
| Temporal Workflow | 跨小时或跨天的人机流程、定时器、补偿、可恢复的多步骤状态机 | 单次事件投递、简单报表生成、仅进程内计算 |
| Transactional Outbox | 本地业务提交后可靠发布跨服务事件；业务记录与 Outbox 必须同事务提交 | 承载人工审批状态、直接执行长任务 |
| Job Table | 单服务内部的导出、清理、校验、聚合等后台任务 | 跨服务事实同步、长时间人机流程 |
| 进程内 goroutine | 可丢弃、无业务状态、进程退出即可取消的短时辅助操作 | 任何要求重启恢复、重试、审计或精确一次效果的工作 |

## Worker 最低契约

1. 领取使用短事务、行锁或等价的原子 Compare-And-Swap；耗时处理不能持有数据库锁。
2. 任务必须有稳定幂等键或稳定业务主键。Worker 可能重复执行，消费端必须以幂等收敛，而不是假设“只执行一次”。
3. 运行态包含租约或锁定时间；进程退出后由其他 Worker 回收过期任务。
4. 自动重试必须有最大次数、指数退避和可重试错误分类；不可重试错误直接进入失败或死信。
5. 人工重试保留原失败记录；重跑创建新任务并关联原任务，不能覆盖历史。
6. 日志必须包含 `request_id`、`trace_id`、`correlation_id`，有事件或工作流时追加 `event_id`、`workflow_id` 和 `business_ref`；不得记录 Token、Cookie、密码或业务文件正文。
7. 指标至少包含 backlog、dead letter、retry、processing duration 和最后成功时间；平台当前 `/metrics` 已输出 Keycloak Outbox 与通用 Job 的 backlog/dead 指标。
8. Worker 监听进程取消信号，停止领取新任务，等待正在处理的任务在受控超时内结束；超时后依赖租约恢复，不能把任务永久留在 RUNNING。

## 失败策略

- 认证、授权、租户边界、金额与权限类强一致判断失败关闭。
- 审计和通知通过本地 Outbox/Inbox 可靠投递，短暂依赖故障不回滚已经提交的业务事实。
- 分析和看板允许显式降级或陈旧读取，但响应必须标明数据时间与降级状态。
- 跨系统业务事实采用“本地事务 + Outbox + 幂等 Inbox/回调 + Reconciliation”，不能使用裸 goroutine 替代。

## Temporal 版本规则

Temporal Workflow 是持久化协议。破坏性分支修改必须使用 `workflow.GetVersion` 或 Worker Build ID/Versioning 的受控路由；Activity 可新增但不能直接删除仍被历史事件引用的实现。上线前必须用历史事件做 Replay 测试，并保留至少一个兼容旧 Build ID 的 Worker，直到旧 Workflow 已完成或迁移。

## 当前实现与剩余项

基础平台 `async_job` 已具备领取、租约恢复、最大重试、退避、失败/死信、取消与人工重跑状态，并持久化 `idempotency_key`、请求摘要、`parent_job_id`、累计重试次数、最后尝试/成功时间和关联追踪字段；Keycloak 授权投影使用独立 Outbox。各子系统仍必须在本地实现同等约束，不应导入基础平台内部包形成新的运行时耦合。
