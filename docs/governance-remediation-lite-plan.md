# 平台治理整改方案（轻量化 · 企业级）

> 日期：2026-09-12 · 性质：**整改方案**（不含代码改动）
> 审计依据：[平台治理能力审计与整改方案](./platform-governance-audit-and-remediation-plan.md)（本次不重复结论，只做范围取舍与落地设计）
> 目标：**用最小的改动面覆盖全部 P0 问题**，并通过"部署闸"把剩下的问题变成可自动发现，而不是靠人工巡检。

---

## 1. 轻量化的三条原则

1. **能在平台侧一次解决的，绝不下发到子系统。** 平台是唯一的公约数；改一次覆盖 5 个子系统。
2. **把"静默失效"变成"启动即失败"。** 企业级的关键不是把功能做全，而是让不合规配置**无法悄悄上线**。
3. **只修"写热点"和"核心链路"，不追求全表/全功能覆盖。** 明确列出本次**不做**的清单（§5），并写清后续触发条件。

按此原则，原始审计的 9 个 P0 项被压缩为 **4 个工作包**，总工作量约 **30–35 人日（2 人 × 2 个迭代）**。

| 冲突语义全量统一 | 只统一新加的版本冲突码，存量不动 | 前端共享层稳定后再收口 |

## 3. 四个工作包

### 包 A｜统一上报契约（审计 + 通知）—— 平台一次定义，子系统各改一处

**为什么轻**：现在的问题是"5 个仓库各写一套"（3 个 endpoint、2 种 scope、fire-and-forget 无重试）。轻量做法是**收敛成一份契约 + 一个共享库**，而不是逐个仓库重写。

**改动**

1. **平台侧（一次成型）**
   - 通知与审计各只保留**一个** endpoint + **一个** scope；对旧路径（`/internal/v1/notifications/events`、错误的 scope）返回 **400 并附带修复指引**，不再静默接受 → 让错误在第一次运行时暴露。
   - 补通知投递自动重试 worker（复用既有 runner 注册模式；`idx_notification_delivery_retry` 已存在但无消费者）。
   - 摄取侧加 **attempt 上限 + 指数退避**，DEAD 事件写入可查询表并对运维可见。
2. **共享 Go 模块 `platformreport`（新）**
   - 内容：审计上报 + 通知上报，**内置本地 outbox 表 + 事务内入队 + 重试 + 幂等键**。
   - 各子系统接入 = 引一个包 + 3 行配置 + 一个 migration（建 outbox 表）。
   - 对标实现直接复用 `customer_and_opportunity` 已经跑通的那套（它是唯一达标的），不新发明。
3. **子系统接入（5 个仓库，每个 1–2 人日）**
   - contract / project / data_analysis：审计改走共享库。
   - project / data_analysis：通知改走共享库（PM 顺带修掉 scope 与 endpoint）。
   - Settlement：**必须**接入——它现在认证路径完全无审计。

**改动量**：平台 3–5 人日 + 共享库 3–5 人日 + 子系统 5–10 人日。

**验收**
- 触发一次项目指派：平台通知中心能看到，且**被指派人**可见。
- 平台通知接口人为返回 5xx：事件不丢、有重试计数、超限进死信。
- **平台停机时下发一次业务操作**：事件留在子系统 outbox，平台恢复后自动补投，平台侧审计出现该记录。

---

### 包 B｜并发基线（只做写热点 + 前端一次收口）

**为什么轻**：不追求全表。定一条约定、改 5 张表、前端改 1 处共享层。

**约定（写进 sharedDocs，作为企业规范）**

```
列：version BIGINT UNSIGNED NOT NULL DEFAULT 1
写：UPDATE ... SET version = version + 1 WHERE tenant_id=? AND id=? AND version=?
     RowsAffected != 1  →  409 <子系统>_VERSION_CONFLICT
读：详情/列表响应必须回传 version
```

**范围（5 张写热点表）**

| 仓库 | 表 | 现状 |
| --- | --- | --- |
| project_management | `pm_project`、`pm_service_item` | 无 version，无条件覆盖 |
| contract_management | `con_contract_template` | 读后写无 CAS → 真丢失更新 |
| Settlement | `settlement_invoice_request` | 开票签发无条件更新 → 静默成功 |
| project_management | `pm_delivery_event` | 加 `UNIQUE(tenant_id, event_id)` 防重投 |

**前端（一处改，三个模块受益）**
在共享 request 层统一：①写请求自动带 `version`；②收到 409 统一提示"数据已被他人修改，请刷新后重试"并触发重载。当前 `project_management`/`data_analysis` 各 0 处处理，`settlement` 0 处文案——这一处改动同时解决三个模块。

**改动量**：迁移 + 写路径 5 人日，前端 2 人日。

**验收**：两个账号同时编辑同一合同模板 / 服务项 / 开票申请，后提交者收到 409 **且界面有明确提示**（不是静默成功）。

---

### 包 C｜身份与权限收敛（三项都是"删代码 / 接现成能力"）

**为什么轻**：都是收口，不是新建功能。

1. **Settlement 目录推送**：照抄 `contract_management/internal/infrastructure/platform/catalog.go`（client_credentials + PUT authorization-catalog），新增 `cmd/authz-catalog`，接入既有发布流程。→ 需求①"所有子系统推送角色权限"才真正落地。
2. **data_analysis 目录去硬编码**：删掉 Go 内硬编码副本，改读 `authz/permission-manifest.yaml`（单一数据源）；把占位桩 `cmd/authz-catalog` 落成真实实现；**CI 加一致性断言**（防再次漂移）。
3. **两个越权修正**：
   - data_analysis `embedbridge/embed.go:76` 的行级范围从硬编码 `TENANT` 改为**取自授权上下文**（否则 `sales_director`/`tech_director` 能看全租户数据）。
   - contract `templates.go:209-211` 删除 `|| hasRole(actor,"admin")` 旁路，改为在平台目录里给 admin 角色显式授权。

**改动量**：6 人日。

**验收**：平台授权中心能看到 Settlement 的 4 角色 / 12 权限；CI 断言 data_analysis 目录与 manifest 一致；用 `sales_director` 登录只能看到本组织数据。

---

### 包 D｜一道部署闸（轻量化的核心）

**为什么轻**：企业级的关键不是"修完所有问题"，而是**让问题无法悄悄上线**。用一道自动门禁替代长期人工巡检。

**做法**：把发布前检查做成可执行脚本 `preflight`（沿用 [本地子系统接入可靠化改造方案](./local-onboarding-hardening-plan.md) 里的 `doctor` 能力），并入 CI/发布流程，**不通过即阻断发布**：

| 检查 | 断言 |
| --- | --- |
| 外网 IP | 实登录一次，断言审计/登录记录 IP **== 客户端公网 IP**，且非 `127.*`、非 `172.16/12` |
| 可信代理 | `APP_TRUSTED_PROXIES` 非空且覆盖实际代理网段（配 `Validate()` fail-closed） |
| 上报就绪 | 各子系统审计/通知凭据已注入；**未配置不得启动**（就绪探针） |
| 目录一致 | 每个子系统的平台目录与仓库 manifest 逐条一致 |
| 并发基线 | 5 张热点表存在 `version` 列 |
| 契约一致 | 通知/审计 endpoint 与 scope 符合统一契约 |

**改动量**：3–5 人日。

**说明**：这道闸同时是"审计独立性"的**轻量替代方案**——不改造流量路径，而是通过"上报就绪 + 缺口监测"保证子系统不会静默不报。若日后审计独立性成为硬合规要求，再评估网关化。

## 4. 排期（2 个迭代）

| 迭代 | 内容 | 出口标准 |
| --- | --- | --- |
| **迭代 1**（2 周） | 包 D（部署闸）+ 包 C（三项收敛）+ 包 A 的平台侧部分 | 发布闸可运行并阻断不合规配置；Settlement 目录已推送；越权已修 |
| **迭代 2**（2 周） | 包 A 的共享库 + 子系统接入 + 包 B（并发基线 + 前端共享层） | 全部 P0 验收清单通过 |

**人力**：2 人（1 平台 + 1 子系统/前端）即可推进；共享库由平台侧牵头，避免 5 个仓库各写一套。

**为什么这样排**：先把"看得见"的（包 D/C）落地，让现状立刻可控；再动"要跨仓库"的（包 A/B）。包 D 先行还能为后续工作提供回归保护。

---

## 5. 企业级保障（不可省的部分）

| 维度 | 要求 |
| --- | --- |
| 契约版本化 | 统一上报契约与并发约定写进 sharedDocs，带版本号；平台对不兼容调用显式报错，不静默兼容 |
| 迁移安全 | 5 张表加 `version` 列均为**可空默认值**的在线 DDL；先在开发/预发执行；保留回滚 SQL |
| 回滚 | 每个工作包独立可回滚；平台侧 fail-loud 改造先在预发开启观察一个发布周期 |
| 可观测 | 上报失败率、投递重试次数、DEAD 数量、409 冲突次数纳入监控面板 |
| 责任归属 | 包 A 共享库由平台侧 owner；子系统接入由各子系统 owner，交付物明确为"接入 + 验收用例通过" |
| 不做假兼容 | 已确认错误的历史路径（如 PM 的 `/internal/v1/...`）**直接删除**，不留兼容分支——否则问题会以"配置不当"的形式长期存在 |

---

## 6. 与完整版的取舍说明

完整审计中列出的 P1/P2 共 20 余项**没有消失**，只是**不在本轮**。它们分三类：

- **会被包 A/B 顺带解决**：通知契约不统一、CRM 队头饥饿（共享库带退避与重试）、frontend 冲突处理缺失。
- **有明确触发条件**（见 §2.2）：哈希链、定向跨系统提醒、流量网关化、归档留存。
- **需要产品决策后再做**：跨系统提醒矩阵、本地收件箱与平台收件箱的去重归属、邮件/短信通道。

建议：**本轮结束后用同一份审计文档做一次复评**，确认哪些 P1 因包 A/B 落地而自动关闭。
