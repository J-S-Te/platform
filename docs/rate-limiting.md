# 平台登录限流配置与部署要求（SEC-B7）

> 源码校准：2026-10-13；限流不代替密码失败锁定、账号生命周期或网关整体容量控制。

## 现状：双桶进程内限流

登录接口（POST /api/v1/auth/login）由 `middleware.LoginRateLimitHTTP("account", 30, 120, time.Minute)` 包装**解密之后**的登录 handler（`router.go` 中先包限流、再由 `WrapJSON` 解密），两层桶语义：

| 桶 | 键 | 阈值 | 计数口径 | 作用 |
| --- | --- | --- | --- | --- |
| 账号桶（先判） | `account:<小写账号>` | 30 次失败/分钟 | **失败-only**：只统计 401；2xx/3xx 成功清零；入口只做预检查、不预增额度 | 主防线：同 IP 多账号互不影响；攻击者轮换出口 IP 也无法重置目标账号额度；正常登录请求无法把他人账号锁死（M-2） |
| IP 兜底桶 | `ip:<客户端IP>` | 120 次/分钟 | 所有请求（无论成败）都计数 | 单出口海量随机账号撞库有上界；阈值高于账号桶，避免 NAT/办公出口正常登录互相拖死 |

账号桶的失败-only 语义：

- 请求进入时只读当前窗口的失败计数做预检查（`count >= 30` 直接 429），本次请求本身不预增账号额度；
- 只有响应为 **401** 时才 +1；2xx/3xx 成功登录清零该账号的失败计数，因此"用正常登录请求刷额度"既不加计数、也不能把账号锁死；
- 账号字段缺失/超长/解析失败的请求无法归因，只计 IP 兜底桶（限流层仅缓冲并原样还原请求体，不触碰密码语义）。

**执行位置（凭据加密模式，SEC-B7 回归）**：账号是登录 JSON 的明文字段；启用凭据加密后，`account` 位于 `credential_envelope` 密文内，解密之前任何中间件都读不到它。若把限流挂在 gin 路由最外层，账号桶会静默退化为只计 IP 桶（等于账号维度限流失效）。因此 `/api/v1/auth/login` 的限流必须包在解密后的 handler 上（`LoginRateLimitHTTP`），未启用加密时使用同一条路径，阈值与计账口径不变。

同一执行位置带来的取舍：解密失败/信封无效的请求在进入本限流器之前就被 `WrapJSON` 拒绝，不落 IP 兜底桶。这条前置路径的放大面由 `/api/v1/auth/credential-challenges` 的独立 IP 桶（120/min）、挑战一次性消费与 `AllowLoginAccount`（解密后 30/min 账号窗口）共同约束；如需对无效信封做 IP 级计量，应在解密外层再挂独立的 IP 固定窗口桶，而不是把登录双桶移回外层。

**残余风险（已知取舍）**：攻击者仍可用 30 次/分钟的失败尝试打满目标账号的窗口，使该账号在窗口内后续登录（含本人正常登录）收到 429。这是"防撞库"与"防被他人锁号/DoS"之间的固有取舍：失败-only 消除了后者，前者只能由窗口时长与阈值共同约束。另需注意：计账发生在响应之后、与入口预检查不在同一临界区，并发请求可少量越过阈值；进程内计数还会因重启/多副本而分散，因此密码失败锁定与入口网关限流不能被本桶替代。

其他限流点：`/oauth2/token` 使用 IP 单桶 60/min；`GET /api/v1/auth/login` 和 `GET /api/v1/auth/oidc/callback` 共用同一 IP 60/min 登录流程限流器（以 Router 实际挂载为准，不是每条路由各有 60 次独立额度）。

## 多副本部署要求（必须）

上述桶是**进程内状态**：

- N 个 API 副本的总额度约为单副本的 N 倍，攻击者可用轮换源 IP 稀释阈值；
- 单副本故障/重启会清空窗口，短时可能出现额度抖动。

因此：**生产多副本部署不得只依赖本中间件**，必须在其一落地：

1. 入口网关/负载均衡层限流（推荐：nginx limit_req 或网关 WAF 按 IP + 账号维度限流）；或
2. 将限流状态迁移到共享存储（Redis 等）——属架构升级，需改造 middleware 接口。

单机/单副本部署仍需核验可信代理、密码失败锁定和网关容量；存在中间件不能据此宣称整个生产安全验收通过。

## 反向代理配置要求（必须）

IP 兜底桶依赖 `RequestClientIP`，其结果由 `APP_TRUSTED_PROXIES` 决定：

- **必须**把真实入口网关（nginx/LB 的容器地址或宿主回环）纳入 `APP_TRUSTED_PROXIES`；
- 若网关未在可信列表内，所有请求对端地址都会退化为网关 IP，"全员共桶"问题会复现；
- **严禁**配置 `0.0.0.0/0` 或 `172.16.0.0/12` 等宽泛网段——任意容器伪造 X-Forwarded-For
  即可劫持他人桶额度（生产/本地模板已收敛为 loopback + 网关精确地址，见
  `deploy/production/.env.example` 与 `docker/.env.local.example`）。
