# 前后端接口协作规范

## 1. 调用与鉴权

前端 API 基地址来自 `VITE_API_BASE_URL`，默认 `/api/v1`。控制台登录成功后由后端通过 `Set-Cookie` 下发 JWT Cookie；所有 API 调用均使用 `credentials: 'include'`。前端不能读取、持久化或手工拼接 Cookie/JWT。

所有请求由后端生成或透传 `X-Request-ID`；响应体中的 `request_id` 用于前后端联调定位。跨域开发环境需使用精确 Origin 白名单和 `Access-Control-Allow-Credentials: true`，不得使用 `*`。

## 2. 统一格式

```json
{
  "code": "OK",
  "message": "操作成功",
  "request_id": "01J...",
  "data": {}
}
```

```json
{
  "code": "AUTH_ACCOUNT_LOCKED",
  "message": "账号已锁定，请稍后再试",
  "request_id": "01J...",
  "details": { "locked_until": "2026-07-16T04:30:00Z" }
}
```

列表查询统一使用：

```text
?page=1&page_size=20&keyword=admin&filter[status]=ACTIVE&sort=-created_at
```

`page` 从 1 开始，`page_size` 默认 20、最大 100。空列表必须返回 `items: []` 和准确的 `total`，不返回 `null`。

## 3. 控制台关键接口

| 前端能力 | 方法与路径 | 后端返回重点 |
|---|---|---|
| 密码登录 | `POST /auth/login` | 未启用 MFA 时返回会话与 `Set-Cookie`；已启用 MFA 时返回 `202`、一次性预认证凭据，不下发 Cookie |
| 钉钉扫码会话 | `POST /auth/dingtalk/qr-sessions` | 匿名创建短时一次性扫码会话；返回 `session_id`、`expires_at`、`render_mode: "dingtalk_frame"` 和仅供发起浏览器使用的 `sdk_config`，并写入浏览器绑定 Cookie |
| 钉钉扫码回调 | `GET /auth/dingtalk/callback` | 原子验证 state、浏览器绑定、过期和一次性消费；始终以顶层 `303 See Other` 跳转结束；普通登录写平台 Cookie，需 MFA 时仅写预认证 Cookie，响应不含认证凭据 |
| 当前登录信息 | `GET /auth/me` | 当前用户、账号、租户、角色、权限摘要 |
| 登录 MFA 验证 | `POST /auth/login/mfa:verify` | 使用预认证凭据与 TOTP/恢复码完成登录；成功后才下发 `Set-Cookie` |
| 高风险操作 MFA | `POST /mfa/step-up/challenges`、`POST /mfa/step-up/challenges:verify` | 返回当前会话的一次性二次验证授权，调用目标接口时放入 `X-MFA-Step-Up-Grant` |
| 退出登录 | `POST /auth/logout` | 撤销当前 `iam_session` 并清理 Cookie |
| 用户与账号 | `GET/POST/PATCH /users`、`GET/POST/PATCH /accounts` | 版本号、状态、账号/任职摘要 |
| 账号密码生命周期 | `POST /accounts/{account_id}/password:initialize`、`POST /accounts/{account_id}/password:reset`、`POST /auth/password:change` | 初始化不回显密码；重置只在成功响应一次性返回临时密码；自主改密后清理 Cookie |
| 组织任职 | `GET/POST/PATCH /org-units`、`/positions`、`/memberships` | 层级、任职类型、生效时间 |
| 角色权限 | `GET/POST/PATCH /roles`、`/role-bindings`、`/permissions` | 权限编码和数据范围 |
| 审计列表 | `GET /audit/events` | 只返回当前页面允许显示的字段 |
| 审计详情 | `GET /audit/events/{id}` | 明细、变更摘要；不返回主体/Request/Trace 字段 |
| 审计导出 | `POST /audit/export-jobs`、`GET /audit/export-jobs/{id}`、`GET /audit/export-jobs/{job_id}/download` | 异步任务状态；完成后通过当前控制台 Cookie 和 `platform:audit:export` 权限下载 CSV |
| 配置中心基础设置 | 配置中心命名空间接口 | 当前发布版本、配置条目、版本号 |
| 平台基础设置 | `GET/PUT /settings/platform` | `organization_name`、`organization_alias`、`timezone`、`qualification` 和 `version` |
| 通知设置 | `GET/PUT /settings/notifications` | `inbox_enabled`、`email_enabled`、`reminder_frequency` 和 `version` |
| 字典管理 | `GET/POST /dictionaries`、`GET/PATCH /dictionaries/{dictionary_id}` | 字典的 `dictionary_id`、编码、名称、状态、项数和版本 |
| 字典项管理 | `GET/POST /dictionaries/{dictionary_id}/items`、`PATCH /dictionaries/{dictionary_id}/items/{item_id}` | 字典项的 `item_id`、编码、标签、值、排序、状态和版本 |
| 运行时字典读取 | `GET /dictionaries/code/{dictionary_code}/items` | 仅返回启用字典下的启用字典项，按 `sort_order` 升序 |
| 登录安全策略 | `GET/PUT /security/login-policy` | 阈值、锁定时长、失败重置窗口和 `version` |
| 锁定账号 | `GET /security/locked-accounts`、`POST /security/locked-accounts/{account_id}/unlock` | 当前锁定账号分页结果；解锁后返回清空的锁定与失败状态 |
| 风险事件 | `GET /security/risk-events`、`POST /security/risk-events/{risk_event_id}/resolve` | 风险状态、处置人、处置时间、处置说明和 `version` |

详细字段以当前目录的[平台接口规范](平台接口规范.yaml)为唯一机器可读接口契约。

## 4. 写操作约束

- 写请求必须使用当前登录主体和租户上下文，禁止由前端传入 `tenant_id`、`created_by`、`updated_by` 覆盖服务端值。
- 更新聚合根时提交 `version`；版本冲突返回 `409` 与模块化错误码。
- 用户、角色、权限、绑定、配置发布、平台设置、通知设置、业务字典和会话安全操作均必须写审计。
- 审计日志没有删除接口。前端的历史 mock 删除行为在接入 API 后必须移除或禁用。
- `POST /accounts` 的 `initial_password`、密码初始化请求的 `password` 和自主改密的 `current_password`/`new_password` 均为敏感写入字段：前端不得记录、缓存、埋点或回显。密码长度为 12 至 128 个 Unicode 字符，必须包含大写字母、小写字母、数字和符号，且不得有空白字符。
- 管理员调用 `POST /accounts/{account_id}/password:reset` 时必须携带当前 `version`。响应中的 `data.temporary_password` 只允许显示给本次操作管理员用于立即复制，必须通过线下安全渠道交付；关闭成功提示后应从组件状态清除，禁止写入 localStorage、sessionStorage、URL、日志、审计或通知。再次请求会生成不同密码。重置会撤销有效会话，但不会解除被锁定账号。
- `POST /auth/password:change` 成功后服务端清理 Cookie，前端应跳转登录页，不得尝试使用旧会话继续调用接口。

## 5. 登录安全与风险控制

- `POST /auth/login` 受单体进程内固定窗口限流（每分钟 30 次）保护。超过限制返回 `429`；前端应提示稍后重试，不得循环重放登录请求。
- 已启用 TOTP MFA 的账号在密码校验通过后，`POST /auth/login` 返回 `202` 和 `data.pre_authentication_credential`，不会写入 Cookie 或创建浏览器会话。前端必须立即调用 `POST /auth/login/mfa:verify`，提交该凭据与 TOTP 动态验证码或恢复码；预认证凭据、challenge、grant、验证码和恢复码均不得写入 localStorage、sessionStorage、URL、日志、埋点或错误上报。
- 高风险操作先调用 `POST /mfa/step-up/challenges` 和 `POST /mfa/step-up/challenges:verify`。验证成功后获得仅绑定当前租户、账号和会话、最长两分钟且只能使用一次的 `data.grant`；调用目标接口时仅通过 `X-MFA-Step-Up-Grant` 请求头携带。授权失败、过期、已使用或主体不匹配均按 `403 AUTH_MFA_STEP_UP_REQUIRED`（过期为 `410`）处理，前端应重新发起二次验证。
- 当前启用 MFA 二次验证的目标操作为：管理员重置密码、登录策略更新、管理员解锁、资源/权限/角色/角色绑定写入、审计导出、OAuth 客户端 JWK 更新、禁用客户端及客户端密钥创建/轮换/禁用。先通过权限校验，再消费二次验证授权；无权限请求不会消耗授权。
- 密码错误统一返回 `401 AUTH_UNAUTHENTICATED`，不得根据账号是否存在显示不同文案；账号已锁定返回 `423 AUTH_ACCOUNT_LOCKED`，`details.locked_until` 为 UTC 解锁时间。
- `GET /security/login-policy` 返回当前租户有效策略；当租户尚未保存策略时，后端返回默认值：失败阈值 5 次、锁定 15 分钟、失败记录滚动重置窗口 30 分钟。`PUT /security/login-policy` 必须提交全部策略字段和 `version`，冲突返回 `409`。
- `GET /security/locked-accounts` 使用 `page`、`page_size`、`keyword` 查询。`POST /security/locked-accounts/{account_id}/unlock` 无请求体；解锁会清除该账号当前锁定状态与有效失败记录。
- `GET /security/risk-events` 使用 `page`、`page_size`、`keyword` 和 `status=OPEN|RESOLVED` 查询。`POST /security/risk-events/{risk_event_id}/resolve` 请求体为 `resolution_comment` 与 `version`；处置说明不能为空，版本冲突返回 `409`。
- 上述安全管理接口均从当前 Cookie 会话读取租户和操作人，前端不得传入 `tenant_id`、`operator_id` 或伪造风险事件处置人。接口权限分别以 OpenAPI 中的 `x-permission` 为准；无权限返回 `403`。

## 6. 平台设置、通知与字典约定

- `GET /settings/platform` 和 `GET /settings/notifications` 在当前租户尚未写入记录时返回可直接展示的默认值；默认读取结果可不包含持久化 `id` 与 `updated_at`。前端首次保存时仍提交页面返回的 `version`（默认值为 `1`）。
- `PUT /settings/platform` 请求体必须包含 `organization_name`、`organization_alias`、`timezone`、`qualification`、`version`。`PUT /settings/notifications` 必须包含 `inbox_enabled`、`email_enabled`、`reminder_frequency`、`version`。提醒频率固定使用 `DAILY`、`EVERY_FOUR_HOURS`、`ONCE`；前端可分别显示为“每日”“每 4 小时”“仅一次”。
- 通知设置不支持短信、SMTP、邮件或 Webhook 发送；历史 `email_enabled` 字段仅用于接口兼容，不代表具备邮件投递能力。站内信模板、消息创建、收件箱列表/详情/未读数/已读和失败重试由独立 `/notifications/...` 接口提供。前端不得调用或展示邮件、短信或 Webhook 发送/测试能力。
- 字典编码和字典项编码使用 1 至 64 位的字母、数字、`.`、`_`、`-`；创建后编码不能通过更新接口修改。字典与字典项的编辑请求均要携带 `version`。当前范围没有删除接口，前端应通过 `status` 启停而不是本地移除记录。
- 列表接口使用 `page`、`page_size`、可选 `keyword` 与 `status`；字典列表中的 `item_count` 为该字典的全部字典项数量，不以启用状态筛选。运行时读取接口只供受控页面按编码获取可选项，不应代替后台管理列表。

## 7. 钉钉第三方企业应用扫码登录约定

钉钉扫码使用独立 `DINGTALK_QR` 提供商，不是 OIDC 配置或登录回调的兼容别名。只有管理员预先绑定的平台账号可以登录；不自动创建用户、账号、任职、角色或权限。

- 前端以 `credentials: include` 调用 `POST /auth/dingtalk/qr-sessions`，请求包含 `tenant_id`、`provider_code` 和受限 `return_to`。成功响应的 `data` 固定为 `session_id`、`expires_at`、`render_mode: "dingtalk_frame"` 与 `sdk_config:{client_id,redirect_uri,response_type:"code",scope,state,prompt?}`；不返回旧式授权地址字段。
- 服务端同时设置短时 HttpOnly 扫码浏览器绑定 Cookie，`SameSite` 固定为 `Lax`；该 Cookie 不是平台会话。state 原文只返回发起浏览器的 `sdk_config`，MySQL 仅保存 `state_hash` 和加密服务端载荷。
- 登录页固定加载钉钉官方 **DTFrameLogin SDK** 并使用 `sdk_config` 渲染内嵌二维码。SDK 成功后，前端必须核验 state 和回调 URL 与本次 `sdk_config` 一致，再由顶层页面导航至 `GET /auth/dingtalk/callback`；不得在内嵌二维码容器内完成平台会话，也不得使用跨窗口消息桥接。
- 回调不是 JSON/HTML 接口，始终以 `303 See Other` 返回：普通成功到经校验的受限 `return_to`；需要 MFA 到 `/login?dingtalk_mfa=1&return_to=...`；失败到 `/login?dingtalk_error=<稳定错误码>`。普通成功按既有配置写平台会话 Cookie；MFA 仅写既有预认证 Cookie；均清除扫码浏览器绑定 Cookie。
- state、授权码、钉钉令牌和原始身份标识均为敏感值。钉钉授权结果不是平台 JWT，原始 `unionId` 不存不记；前端不得写入浏览器存储、URL、日志或埋点，后端不得写入 Cookie、日志或审计详情。
- 管理配置、哈希、审计、Cookie、错误码和环境变量的完整约束以 `钉钉第三方企业应用扫码登录开发说明.md` 与 OpenAPI 中的两个钉钉 operation 为准。

## 8. P1 占位约定

审计接收状态、服务遥测与告警规则的路径已写入 OpenAPI，但默认可能返回 `501 PLATFORM_CAPABILITY_NOT_ENABLED`。前端收到该错误应展示“能力待后端启用”，不得伪造成功保存或修改本地状态。身份增强接口已实现：外部身份提供商本地配置/绑定、TOTP、恢复码、独立挑战验证、同意查询/授予/撤销、`private_key_jwt`、PAR/JAR、独立 post-logout URI 注册和客户端公钥管理。外部 IdP 第三方回调与断言验签、实际 Vue 同意页、可配置 IP/网络登录策略与失败关闭仍属于后续 P1。密码登录 MFA 强制与高风险操作二次验证已落地。

### 7.1 身份增强联调约定

- 外部身份管理接口位于 `/api/v1/identity-providers` 与 `/api/v1/users/{user_id}/external-identities`。`external_subject` 仅允许管理员在绑定请求中提交；响应、审计展示和日志均不得回显该值。当前后端只提供本地提供商配置和绑定控制面，业务前端不得假定已经存在第三方登录跳转。
- MFA 接口仅作用于当前已登录账号：`POST /api/v1/mfa/totp:prepare` 返回一次性注册密钥与 `provisioning_uri`，前端必须只在当前确认页面显示、不得落盘或写日志；`totp:confirm` 的 `recovery_codes` 也只显示一次。
- 同意页使用根路径 `GET /oauth2/consent` 查询，提交使用表单编码 `POST /oauth2/consent/grant`，撤销使用 `DELETE /oauth2/consent?client_id=...`。两个写接口必须携带浏览器 `Origin`，且只接受与 `OIDC_ISSUER` 同源的请求；前端页面尚未交付前不得绕过该校验。
- OAuth Client 的普通 `redirect_uris` 与 `post_logout_redirect_uris` 是两个独立集合，均以 `version` 乐观锁整体替换。客户端 JWK 只允许提交公钥材料；任何私钥字段均会被拒绝。

## 9. 子系统后端接入接口约定

本文件第 1 至 7 节主要约束控制台前后端；下列接口属于**子系统后端到平台后端**通信，前端页面、浏览器和 Cookie 会话不得调用：

- 统一登录浏览器入口：`GET /authorize`（根路径，不带 `/api/v1`）；
- Token 获取：`POST /oauth2/token`（根路径，不带 `/api/v1`）；
- 审计单条接收：`POST /api/v1/audit/events`；
- 审计批量接收：`POST /api/v1/audit/events:batch`。

跨应用统一登录将**业务落地目标**与 **OIDC 协议回调**分离：`ApplicationEnvironment` 下的 `platform_application_login_target(target_code → target_uri)` 仅用于服务端受控落地解析；`OAuth Client → 精确 redirect_uri` 仅用于 `/authorize` 回传授权码。`target_uri` 不得作为或覆盖 `redirect_uri`，`/authorize` 不接收 `target_code`、`target_uri`、`return_to`、`target_url` 或其他动态跳转参数。子系统以随机 `state` 关联一次性本地登录事务（可关联已校验的 `target_code`，不能包含原始目标 URL），平台只原样返回。登录目标解析必须在服务端以 `(tenant_id, application_id, environment_id, target_code)` 精确匹配 ACTIVE 记录；当前不发布独立的浏览器或匿名解析 HTTP 接口。PKCE 仅允许 `S256`，不得把任何凭据、用户标识或原始目标 URL 放入 `state`。

审计上报使用由 `client_credentials` 签发、具备 `audit.ingest` 的应用 Bearer Token。接收端先校验 JWT 的 Ed25519（`EdDSA`）签名、`iss`、`aud`、`token_use=application` 与时间声明，再以数据库当前启用的 OAuth Client、Application、ApplicationEnvironment 精确复核令牌中的客户端、租户、应用、环境和 scope；控制台 Cookie、用户 Bearer Token、已停用客户端或过期数据库绑定均不能调用该接口。

每个请求必须提交 `X-Request-ID`、`traceparent` 与 `X-Correlation-ID`；`traceparent` 只接受 55 字符、四段小写十六进制的 W3C 基础格式，并拒绝 `ff` 版本、全零 trace-id、全零 parent-id、额外字段和大写字符。单条上报的三个头必须与事件体的 `request_id`、`trace_id`、`correlation_id` 对应；批量头只表示本次 Outbox 投递动作，每条事件体始终保留自己的原始链路字段。

事件请求体使用严格字段集：必须显式传入且精确匹配令牌的 `application_code`、`environment_code`，但**不得传入 `client_id` 或 `tenant_id`**；平台从可信应用主体注入内部 `client_id`。批量最多 100 条、请求体最多 256 KiB，并以 `(application_id,event_id)` 逐项幂等去重。批量先完成所有事件校验；任一事件不合法即返回 `422`，不产生部分事件或投递回执。全部合法时，事件去重结果和内部 `audit_ingestion_receipt` 在同一事务中写入，回执记录投递三元组、`event_count`、`accepted_count`、`duplicate_count` 和 `COMPLETED` 状态；重复事件为成功的逐项 `DUPLICATE`。该内部回执当前没有对外查询、创建或管理接口。详细字段、禁止字段和状态码以 OpenAPI 中这两个 operation 为准。
