# 基础能力平台：系统集成接口调用手册

> **适用对象**：接入本平台的子系统后端开发人员、平台后端开发人员、联调与运维人员。  
> **文档目的**：把当前项目已经实现或已经纳入接口契约的调用格式、认证边界、错误格式和外部接入流程集中说明，便于后续系统按统一方式调用。  
> **不新增接口**：本文不定义任何新路径、字段、权限或认证方式。具体字段、枚举和接口变更以 OpenAPI 契约及实际路由实现为准。

## 1. 阅读前须知

### 1.1 契约来源与优先级

| 优先级 | 文件/代码 | 用途 |
|---|---|---|
| 1 | `backend/internal/transport/http/router.go` | 当前服务实际注册的 HTTP 路由、认证中间件、权限与限流边界。 |
| 2 | `docs/03_接口规范/平台接口规范.yaml` | OpenAPI 3.1 契约；包含请求/响应 Schema、参数、OAuth/OIDC 协议端点说明。适合导入接口工具或生成客户端。 |
| 3 | `docs/03_接口规范/接口文档.md` | 面向开发人员的接口目录、调用约束及 DTO 摘要。 |
| 4 | 本文 | 面向系统集成的调用说明和格式提取，不替代以上来源。 |

如本文与运行代码或 OpenAPI 不一致，应以**实际路由实现**和 `平台接口规范.yaml` 为准，并同步修订本文。

### 1.2 地址与版本前缀

假设平台部署地址为 `https://<platform-host>`：

| 类别 | 地址形式 | 说明 |
|---|---|---|
| 平台 REST API | `https://<platform-host>/api/v1/...` | 管理、认证、审计、配置等平台 API 使用此版本前缀。 |
| OAuth/OIDC 授权端点 | `https://<platform-host>/authorize` | **不带** `/api/v1`。浏览器跳转端点。 |
| OAuth/OIDC 令牌端点 | `https://<platform-host>/oauth2/token` | **不带** `/api/v1`。令牌交换端点。 |
| OIDC 发现文档 | `https://<platform-host>/.well-known/openid-configuration` | **不带** `/api/v1`。客户端应从该文档获取 issuer、JWKS 等协议地址。 |
| 健康检查 | `https://<platform-host>/healthz`、`https://<platform-host>/readyz` | **不带** `/api/v1`。用于探针，不作为业务鉴权接口。 |

**不要**把 `/authorize`、`/oauth2/token` 等 OAuth/OIDC 协议地址拼接到 `/api/v1` 后；也不要为后续系统自行推断未发布的 `/api/v1` 路径。

### 1.3 调用方类型与可用接口

| 调用方 | 可用认证方式 | 适用接口 | 重要限制 |
|---|---|---|---|
| 浏览器控制台/平台前端 | 平台会话 Cookie | `/api/v1` 下的已授权控制面接口 | 后端从 Cookie 读取认证会话；浏览器 JWT 不作为 `Authorization` Bearer 传递。 |
| 子系统后端（机器到机器） | OAuth 2.0 `client_credentials` 取得的应用 Bearer Token | 当前明确开放给子系统的审计接入：`POST /api/v1/audit/events`、`POST /api/v1/audit/events:batch` | Token 必须含 `audit.ingest` scope；用户 Cookie 不能替代该 Token。 |
| OAuth/OIDC 客户端应用 | OAuth/OIDC 协议调用 | `/authorize`、`/oauth2/token`、`/oauth2/revoke`、发现文档、JWKS、userinfo 等 | 协议端点不使用平台通用 JSON 信封；必须按 OAuth/OIDC 规范处理。 |
| 运维探针 | 无认证 | `/healthz`、`/readyz` | 仅检查可用性；不要以它们验证授权或业务数据。 |

> **边界结论**：当前“其他系统”不能使用任意一个应用 Bearer Token 调用所有 `/api/v1` 管理接口。应用 Bearer Token 的已发布机器接入边界是审计写入接口；用户、组织、角色、配置、字典等控制面接口仍由平台登录会话、权限码和部分场景的 MFA Step-Up 保护。

## 2. 通用 REST 格式

### 2.1 请求约定

本文列出的 JSON 业务接口使用以下格式；文件上传、文件下载及 OAuth/OIDC 协议端点属于例外，必须以对应 OpenAPI `requestBody` 或响应定义为准：

```http
Accept: application/json
Content-Type: application/json
```

- 时间字段使用 **UTC RFC 3339** 格式，例如 `2026-07-22T08:30:00Z`。
- 平台从会话或应用凭据中解析 `tenant_id`，调用方不得在请求中传入 `tenant_id` 试图覆盖租户上下文。
- 请求 DTO 是否拒绝未声明字段，以对应 OpenAPI Schema 与处理器为准；外部审计接入 DTO 已明确采用严格字段校验，不能附带未定义字段。
- 写接口中的 `version` 是乐观锁版本号时，必须先读取资源，再把读取结果中的最新 `version` 原样带回更新请求；冲突时不能盲目重试旧数据。
- 密码、`client_secret`、JWT、Cookie、MFA 密钥、恢复码、刷新令牌和 Step-Up Grant 都是敏感数据，不得写入业务日志、审计摘要、异常详情或浏览器持久化存储。

### 2.2 平台通用成功响应

一般 `/api/v1` JSON 接口以如下信封返回：

```json
{
  "code": "OK",
  "message": "操作成功",
  "request_id": "服务端请求标识",
  "data": {}
}
```

| 字段 | 类型 | 含义 | 调用方处理方式 |
|---|---|---|---|
| `code` | string | 成功时固定为 `OK`。 | 用于程序判断成功结果。 |
| `message` | string | 面向调用者的结果说明。具体文案随操作不同。 | 不应作为稳定业务判断条件。 |
| `request_id` | string | 服务端处理本次请求的关联标识。 | 建议记录在调用日志中，排障时提供给平台方。 |
| `data` | object / array / scalar | 具体接口返回的数据。 | 按对应接口的 OpenAPI response schema 解析。 |

> `202 Accepted` 也使用同一成功信封；它表示平台已接收请求，不代表所有异步后续动作都已完成。

### 2.3 平台通用错误响应

一般 `/api/v1` JSON 接口失败时使用如下信封：

```json
{
  "code": "PLATFORM_VALIDATION_ERROR",
  "message": "请求参数不合法",
  "request_id": "服务端请求标识",
  "details": {}
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `code` | string | 稳定错误代码，应优先用于程序分类。 |
| `message` | string | 面向调用者的安全错误信息。 |
| `request_id` | string | 本次失败请求的服务端关联标识。 |
| `details` | 任意 JSON，可能缺省 | 附加的安全错误详情；调用方不能假定所有错误均有此字段或固定结构。 |

当前接口文档列出的常见 HTTP 状态与错误代码如下：

| HTTP 状态 | 常见 `code` | 推荐处理 |
|---:|---|---|
| 401 | `AUTH_UNAUTHENTICATED` | Cookie 会话失效时重新登录；应用 Token 失效时重新获取 Token。不要把 Token 写入日志。 |
| 403 | `AUTH_FORBIDDEN` | 当前主体无权限、无 scope 或认证边界不匹配；不要自动改用其他认证方式重试。 |
| 404 | `PLATFORM_NOT_FOUND` | 校验路径参数、资源标识及其租户范围。 |
| 405 | `PLATFORM_METHOD_NOT_ALLOWED` | 校验 HTTP 方法。 |
| 409 | `IAM_CONFLICT`、`IAM_VERSION_CONFLICT` | 并发更新冲突；重新读取最新资源并由业务确认后再提交。 |
| 413 | 以服务端返回的 `code` 为准 | 请求体超过接口允许的最大字节数；缩小请求体。审计批量上报还受事件数量和 256 KiB 总体积限制。 |
| 422 | `PLATFORM_VALIDATION_ERROR` | 按接口字段规则修复请求后再提交；不要用猜测字段绕过校验。 |
| 500 | `PLATFORM_INTERNAL_ERROR` | 记录 `request_id` 后联系平台维护方。 |
| 503 | `PLATFORM_DEPENDENCY_UNAVAILABLE` | 依赖暂不可用；由调用方按自身可靠性策略延迟重试。 |

### 2.4 不使用通用信封的端点

下列类型不能按第 2.2 节的 `code/message/request_id/data` 格式解析：

| 端点/类别 | 实际格式 |
|---|---|
| `/authorize` | 浏览器重定向（302）或 OAuth 错误响应。 |
| `/oauth2/token` | OAuth 2.0 Token JSON，例如 `access_token`、`token_type`、`expires_in`、`scope`。 |
| `/oauth2/revoke` | RFC 7009 撤销结果；成功时为 200 空响应。 |
| `/.well-known/openid-configuration`、`/oauth2/jwks` | OIDC Discovery / JWKS 协议 JSON。 |
| `/oauth2/userinfo` | OIDC UserInfo JSON 或 OAuth 协议错误。 |
| `/api/v1/audit/export-jobs/{job_id}/download` | 文件流及 `Content-Disposition`，不是 JSON 信封。 |

### 2.5 文件上传格式：`POST /api/v1/files`

该接口是**平台控制面 Cookie 接口**，由 `platform:file:upload` 权限保护，不是当前对其他系统开放的应用 Bearer Token 接口。请求必须使用 `multipart/form-data`，不能按 JSON 提交，也不应手工指定 multipart boundary。

| 表单字段 | 必填情况 | 当前运行代码的要求 | 说明 |
|---|---|---|---|
| `file` | 必填 | 必填 | 上传的二进制文件。服务端以文件内容、扩展名和声明的 MIME 类型共同校验。 |
| `application_id` | 必填 | 必填 | 目标应用标识；不能为空、不能包含路径分隔符。 |
| `classification` | 以运行代码为准 | 可不传 | 传入时仅接受 `INTERNAL`、`CONFIDENTIAL`、`RESTRICTED`。 |

当前后端文件服务默认仅接受 `application/pdf`、`image/jpeg`、`image/png`、`text/plain`、`text/csv`；文件内容最大为 **20 MiB**，整个 multipart HTTP 请求最大为 **21 MiB**（为 multipart 开销预留空间）。成功时返回 `201 Created` 及平台成功信封；下载 `GET /api/v1/files/{file_id}/content` 返回文件流。

> **契约差异需在联调前确认**：当前 OpenAPI 将 `classification` 标注为必填，并包含 `PUBLIC` 枚举；当前运行代码要求 `application_id` 必填、允许省略 `classification`，且非空 `classification` 不接受 `PUBLIC`。在该差异修复或发布统一版本前，调用方应遵循实际部署的后端校验，不要假设 OpenAPI 中的 `PUBLIC` 可用。

## 3. 认证与授权格式

### 3.1 平台会话 Cookie（控制台接口）

平台控制台登录成功后，服务端以 HttpOnly 会话 Cookie 维护会话，Cookie 名称由 `AUTH_SESSION_COOKIE_NAME` 配置，默认值为 `bp_session`。

适用范围：管理用户、组织、角色、配置、字典、审计查询、平台设置等控制面接口。

调用注意事项：

1. 浏览器客户端必须按同源/CORS 策略携带 Cookie 凭据。
2. 后端认证中间件从配置的 Cookie 中读取平台 JWT 会话；不要把该 JWT 改放进 `Authorization: Bearer ...` 请求头。
3. 某些高风险路由还要求一次性 `X-MFA-Step-Up-Grant`。该值与租户、账号、会话绑定，只能用于紧随其后的一个目标请求，不能缓存或复用。
4. 平台控制台 Cookie 不能用于外部审计接入接口。

### 3.2 应用 Bearer Token（子系统审计接入）

子系统后端调用审计接入接口时，必须先通过 OAuth 2.0 Client Credentials 获取应用 Token，再以标准 Bearer 形式传递：

```http
Authorization: Bearer <access_token>
```

服务端会校验 Token 的签名、`iss`、`aud`、用途、有效期、scope，以及 Token 与当前 OAuth Client / Application / Environment 的有效绑定。调用方不得伪造或在审计 JSON 中传入 `tenant_id`、`client_id` 来替代该绑定。

审计接入所需 scope：

```text
audit.ingest
```

### 3.3 获取机器 Token：`POST /oauth2/token`

**用途**：子系统以 OAuth Client 凭据取得调用审计接入接口的短期 Bearer JWT。

| 项目 | 格式 |
|---|---|
| 方法 | `POST` |
| 地址 | `https://<platform-host>/oauth2/token` |
| Content-Type | `application/x-www-form-urlencoded` |
| 客户端认证 | `Authorization: Basic <Base64(client_id:client_secret)>`，`client_credentials` 必须使用 HTTP Basic。 |
| 请求字段 | `grant_type=client_credentials`；可携带 `scope` 申请范围。 |
| 成功响应 | OAuth Token JSON，不使用平台通用信封。 |

示例（`<...>` 均为部署时分配的实际值，不是可直接使用的凭据）：

```bash
curl --request POST 'https://<platform-host>/oauth2/token' \
  --header 'Authorization: Basic <base64(client_id:client_secret)>' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'scope=audit.ingest'
```

成功返回格式：

```json
{
  "access_token": "<short-lived-bearer-jwt>",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "audit.ingest"
}
```

| 字段 | 必有 | 说明 |
|---|---:|---|
| `access_token` | 是 | 短期 Bearer JWT。仅在服务器内存或受控密钥存储中短暂保存。 |
| `token_type` | 是 | 当前值为 `Bearer`。 |
| `expires_in` | 是 | Access Token 剩余有效期，单位秒。 |
| `scope` | 是 | 实际签发的、以空格分隔的 scope。调用审计接口前必须确认其中包含 `audit.ingest`。 |
| `refresh_token` | 否 | 仅授权码或刷新令牌相关流程可能返回；Client Credentials 成功响应不能依赖该字段。 |
| `id_token` | 否 | OIDC 用户登录相关流程可能返回；机器审计接入不依赖该字段。 |

**失败格式**：OAuth 端点使用协议错误对象，而不是平台错误信封：

```json
{
  "error": "invalid_client"
}
```

当前契约中的 `error` 值包括：`invalid_request`、`invalid_grant`、`invalid_token`、`unsupported_grant_type`、`invalid_client`、`unauthorized_client`、`invalid_scope`、`server_error`。

## 4. 外部系统审计接入（当前机器调用接口）

### 4.1 接口概览

| 接口 | 方法 | 认证 | 成功状态 | 用途 |
|---|---|---|---:|---|
| `/api/v1/audit/events` | `POST` | 应用 Bearer Token + `audit.ingest` | 202 | 上报一条审计事件。 |
| `/api/v1/audit/events:batch` | `POST` | 应用 Bearer Token + `audit.ingest` | 202 | 批量上报 1–100 条审计事件。 |

这两条接口是**子系统后端专用**接口，不应由浏览器前端直接调用。Token 中绑定的租户、应用、环境是接收边界：正文中的 `application_code`、`environment_code` 必须和 Token 绑定值精确一致。

### 4.2 审计接入固定请求头

两条审计接入接口均要求以下请求头：

| 请求头 | 是否必填 | 格式与规则 |
|---|---:|---|
| `Authorization` | 是 | `Bearer <access_token>`；Token 必须通过 Client Credentials 获取并具有 `audit.ingest`。 |
| `Content-Type` | 是 | `application/json`。 |
| `X-Request-ID` | 是 | 1–128 位，匹配 `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`。作为本次投递请求标识。 |
| `traceparent` | 是 | W3C 四段基础格式：`<version>-<trace-id>-<parent-id>-<flags>`。四段均为小写十六进制；`trace-id` 是非全零 32 位，`parent-id` 是非全零 16 位，`version` 不能为 `ff`。服务端取第二段作为 trace ID。 |
| `X-Correlation-ID` | 是 | 与 `X-Request-ID` 相同的标识规则；用于跨系统业务关联。 |

合法的 `traceparent` 形态示例（仅展示格式）：

```text
00-<32位小写非零trace-id>-<16位小写非零parent-id>-01
```

不要把用户信息、密码、Token、Cookie、客户端密钥或 URL 放进 `X-Request-ID`、`traceparent` 或 `X-Correlation-ID`。

### 4.3 单条事件：`POST /api/v1/audit/events`

#### 4.3.1 单条请求一致性要求

单条上报时，正文中的下列字段必须与传输请求头表达的值一致：

| 正文字段 | 必须等于 |
|---|---|
| `request_id` | `X-Request-ID` |
| `trace_id` | `traceparent` 的第二段 `trace-id` |
| `correlation_id` | `X-Correlation-ID` |

同时，`actor_type`、`request_id`、`trace_id`、`correlation_id` 均为必填。任一字段遗漏、格式非法或三元关联不一致时，服务端返回 422，事件不会作为有效事件接收。

#### 4.3.2 请求 JSON 字段

以下表格是 `AuditEventInput` 的完整字段格式。

| 字段 | 类型 | 必填 | 约束/说明 |
|---|---|---:|---|
| `event_id` | string | 是 | ULID；由子系统生成的稳定事件标识。在同一应用内不可复用。它是幂等键的一部分。 |
| `occurred_at` | string | 是 | UTC RFC 3339 事件发生时间。 |
| `application_code` | string | 是 | 正则 `^[a-z][a-z0-9_-]{1,63}$`；必须与 Bearer Token 的 application code 精确一致。 |
| `environment_code` | string | 是 | 正则 `^[a-z][a-z0-9_-]{1,31}$`；必须与 Bearer Token 的 environment code 精确一致。 |
| `actor_type` | string | 是 | 枚举：`USER`、`ACCOUNT`、`SERVICE`、`SYSTEM`。 |
| `actor_id` | string | 否 | 最大 128；主体稳定标识。`SYSTEM` 可省略。 |
| `actor_name` | string | 否 | 最大 200；仅脱敏展示名，不能填写完整身份证号、手机号、邮箱等个人信息。 |
| `session_id` | string | 否 | 最大 128；仅可填写不可逆会话标识，不能填写 Cookie、JWT 或原始会话凭据。 |
| `action` | string | 是 | 最大 128；正则 `^[A-Za-z0-9:._-]{1,128}$`。 |
| `resource_type` | string | 是 | 最大 64。 |
| `resource_id` | string | 否 | 最大 128。 |
| `resource_name` | string | 否 | 最大 200。 |
| `business_id` | string | 否 | 最大 128。 |
| `request_id` | string | 是 | 1–128；匹配关联标识规则，且必须与 `X-Request-ID` 相同。 |
| `trace_id` | string | 是 | 32 位非全零小写十六进制，且必须等于 `traceparent` 的 trace ID。 |
| `correlation_id` | string | 是 | 1–128；匹配关联标识规则，且必须与 `X-Correlation-ID` 相同。 |
| `result` | string | 是 | 枚举：`SUCCESS`、`FAILURE`、`DENIED`。 |
| `reason_code` | string | 否 | 最大 128。 |
| `risk_level` | string | 否 | 枚举：`LOW`、`MEDIUM`、`HIGH`、`CRITICAL`。 |
| `classification` | string | 否 | 最大 64。 |
| `summary` | string | 否 | 最大 1000；仅最小化业务摘要，不能包含敏感凭据、完整个人信息、原始请求或原始响应。 |
| `change_summary` | array | 否 | 最多 100 项；每项为字段变化摘要，格式见下一表。 |
| `metadata` | object | 否 | 最多 40 个属性；只允许一层标量摘要，格式见下一表。 |

`change_summary` 单项格式：

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `field` | string | 是 | 1–128；字段名不得匹配密码、secret、token、cookie、authorization、credential、private key、access key、refresh token 等敏感关键字。 |
| `label` | string | 否 | 最大 128。 |
| `operation` | string | 是 | `CREATE`、`UPDATE`、`DELETE` 之一。 |
| `before` | string | 否 | 最大 512；仅允许已按字段策略脱敏的旧值。 |
| `after` | string | 否 | 最大 512；仅允许已按字段策略脱敏的新值。 |
| `masked` | boolean | 否 | 默认 `false`。 |

`metadata` 规则：

- 键名长度 1–64，不能匹配敏感关键字（密码、Token、Cookie、Authorization、凭据、私钥、客户端密钥等）。
- 值只能是 string（最长 512）、number、integer、boolean 或 `null`。
- 不允许嵌套对象、原始 HTTP 请求/响应、堆栈、二进制内容和敏感信息。

#### 4.3.3 单条调用示例

下面示例中的尖括号字段由接入系统在运行时生成或配置；示例只说明格式。

```bash
curl --request POST 'https://<platform-host>/api/v1/audit/events' \
  --header 'Authorization: Bearer <access_token>' \
  --header 'Content-Type: application/json' \
  --header 'X-Request-ID: <request_id>' \
  --header 'traceparent: 00-<32位小写非零trace-id>-<16位小写非零parent-id>-01' \
  --header 'X-Correlation-ID: <correlation_id>' \
  --data @- <<'JSON'
{
  "event_id": "<stable_ulid>",
  "occurred_at": "2026-07-22T08:30:00Z",
  "application_code": "<application_code>",
  "environment_code": "<environment_code>",
  "actor_type": "SYSTEM",
  "action": "ORDER:CREATE",
  "resource_type": "ORDER",
  "resource_id": "<business_resource_id>",
  "request_id": "<request_id>",
  "trace_id": "<32位小写非零trace-id>",
  "correlation_id": "<correlation_id>",
  "result": "SUCCESS",
  "risk_level": "LOW",
  "summary": "订单创建完成",
  "metadata": {
    "channel": "api",
    "status_code": 201
  },
  "change_summary": [
    {
      "field": "status",
      "operation": "CREATE",
      "after": "CREATED"
    }
  ]
}
JSON
```

成功返回 HTTP `202 Accepted`，使用平台成功信封，`data` 为单条回执：

```json
{
  "code": "OK",
  "message": "审计事件已接收",
  "request_id": "<delivery_request_id>",
  "data": {
    "event_id": "<stable_ulid>",
    "status": "ACCEPTED"
  }
}
```

`data.status` 的取值：

| 值 | 含义 | 调用方处理 |
|---|---|---|
| `ACCEPTED` | 该稳定事件标识首次被接收。 | 将本地待投递记录标记为已确认。 |
| `DUPLICATE` | 同一 application 内已接收过相同 `event_id`。 | 这是幂等成功，不能当作失败重建事件或生成新的 `event_id`。 |

#### 4.3.4 幂等性

- 去重键是**同一 application + `event_id`**。
- 重复提交同一个事件标识时，响应仍为 `202`，并在 `data.status` 返回 `DUPLICATE`。
- 调用方必须在首次产生业务事件时持久化稳定 `event_id`；网络超时或重试时复用同一个 `event_id`。
- 不要以“请求体内容哈希”替代 `event_id`，也不要因为收到 `DUPLICATE` 而新建另一个事件标识。

### 4.4 批量事件：`POST /api/v1/audit/events:batch`

批量请求体：

```json
{
  "events": [
    {
      "event_id": "<stable_ulid_1>",
      "occurred_at": "2026-07-22T08:30:00Z",
      "application_code": "<application_code>",
      "environment_code": "<environment_code>",
      "actor_type": "SYSTEM",
      "action": "ORDER:CREATE",
      "resource_type": "ORDER",
      "request_id": "<original_business_request_id_1>",
      "trace_id": "<original_32位小写trace-id_1>",
      "correlation_id": "<original_business_correlation_id_1>",
      "result": "SUCCESS"
    }
  ]
}
```

批量与单条的区别：

| 项目 | 规则 |
|---|---|
| `events` 数量 | 最少 1 条，最多 100 条。 |
| HTTP Body | 整个 HTTP 请求体最大 256 KiB。 |
| 请求头三元组 | `X-Request-ID`、`traceparent`、`X-Correlation-ID` 表示**本次批量投递动作**。 |
| 事件正文三元组 | 每条事件仍必须填写自身原始 `actor_type`、`request_id`、`trace_id`、`correlation_id`；批量模式下不要求逐项等于本次投递请求头。 |
| 原子性 | 服务端先校验整个批次；任一事件不合法则返回 422，不写入任何事件或批量投递回执。 |
| 去重 | 对每个事件按同一 application + `event_id` 独立去重。 |
| 响应顺序 | 回执数组顺序与 `events` 输入顺序一致。 |

成功时返回 HTTP `202 Accepted`：

```json
{
  "code": "OK",
  "message": "审计事件已接收",
  "request_id": "<delivery_request_id>",
  "data": [
    {
      "event_id": "<stable_ulid_1>",
      "status": "ACCEPTED"
    },
    {
      "event_id": "<stable_ulid_2>",
      "status": "DUPLICATE"
    }
  ]
}
```

### 4.5 推荐的可靠投递顺序

当前仓库中的审计接入契约支持稳定事件标识与幂等确认。对接系统应按如下顺序设计自己的投递过程：

1. 业务动作发生时，在本系统可靠保存待上报事件及其稳定 `event_id`。
2. 生成或携带该业务动作的 `request_id`、`trace_id`、`correlation_id`，确保三者不含敏感信息。
3. 通过 Client Credentials 获取未过期且包含 `audit.ingest` 的 Access Token。
4. 组装单条或批量请求；单条上报时让正文三元组与请求头三元组完全一致。
5. 收到 `202 + ACCEPTED` 或 `202 + DUPLICATE` 后，将对应本地事件标记为已确认。
6. 遇到网络不确定、超时或 5xx 时，重试时必须复用原 `event_id`，而不是创建新事件。
7. 遇到 401、403、422、413、409 等明确客户端问题时，先修复认证、权限、字段或批次大小；不要无限重试同一坏请求。

## 5. OAuth/OIDC 对接格式

### 5.1 何时使用 OAuth/OIDC

- 子系统需要把平台作为统一登录/身份提供方时，使用 OpenID Connect Authorization Code Flow。
- 子系统后端需要获取机器身份来上报审计时，使用 OAuth 2.0 Client Credentials。
- 当前 `/authorize` 只接受 OAuth Client 的**精确登记** `redirect_uri`；它不接收 `target_code`、`target_uri`、`return_to`、`target_url` 等自定义跳转参数。

### 5.2 浏览器授权：`GET /authorize`

该端点不使用 `/api/v1` 前缀，主要参数如下：

| Query 参数 | 必填 | 格式/规则 |
|---|---:|---|
| `response_type` | 是 | 固定 `code`。 |
| `client_id` | 是 | 已登记 OAuth Client 标识，最大 255。 |
| `redirect_uri` | 是 | 必须与该 Client 已启用的登记值按**完整字符串精确相等**；不能使用通配符、前缀匹配或查询参数拼接。 |
| `scope` | 是 | 空格分隔；OIDC 登录必须包含 `openid`，且所有 scope 必须已授权给该 Client。 |
| `state` | 是 | 16–2048；由客户端生成的随机关联值，平台原样返回。不能放用户信息、密码、令牌、Cookie、密钥或可重放凭据。 |
| `nonce` | 否 | 最大 255。 |
| `code_challenge` | 是 | PKCE 挑战值，长度 43–128，字符集 `[A-Za-z0-9_-]`。 |
| `code_challenge_method` | 是 | 固定 `S256`。 |

成功后平台只会重定向到精确登记的 `redirect_uri`，并附带一次性 `code` 和原样 `state`。授权码、Cookie、Access Token、Refresh Token 和客户端密钥不能出现在 URL、`state` 或重定向参数中。

### 5.3 令牌交换：`POST /oauth2/token`

| `grant_type` | 必要字段 | 客户端认证规则 |
|---|---|---|
| `authorization_code` | `code`、精确 `redirect_uri`；若该授权码使用 PKCE，还需 `code_verifier` | confidential 客户端使用 HTTP Basic；public 客户端仅在表单传 `client_id`。不接受 `client_secret` 表单字段。 |
| `refresh_token` | `refresh_token` | confidential 客户端使用 HTTP Basic；public 客户端仅在表单传 `client_id`。刷新成功时令牌轮换。 |
| `client_credentials` | 可带 `scope` | 必须使用 HTTP Basic。 |

成功响应与错误响应见第 3.3 节。协议客户端应以 `error` 字段处理 OAuth 失败，而不是期待平台的 `code/message/data` 信封。

### 5.4 Discovery、JWKS、UserInfo 与撤销

| 端点 | 作用 | 调用说明 |
|---|---|---|
| `GET /.well-known/openid-configuration` | OIDC Discovery | OIDC 客户端应读取此文档中的 `issuer`、授权端点、Token 端点、JWKS 地址及支持能力。 |
| `GET /oauth2/jwks` | JWKS | 供资源服务器/客户端获取签名公钥集以校验 JWT。 |
| `GET/POST /oauth2/userinfo` | OIDC UserInfo | 使用 Access Token 获取已授权声明；按 OpenID Connect 协议处理。 |
| `POST /oauth2/revoke` | Token 撤销 | confidential Client 必须使用 HTTP Basic；表单必须有 `token`，可选 `token_type_hint` 为 `access_token` 或 `refresh_token`。对未知、过期或已撤销 Token 仍返回 200，避免泄露 Token 是否存在。 |
| `GET/POST /oauth2/logout` | OIDC 会话退出 | 按端点契约处理浏览器会话与跳转。 |

## 7. 后端实现与联调检查清单

### 7.1 外部系统接入前

- [ ] 平台侧已登记并启用对应 Application、Environment、OAuth Client 与 scope。
- [ ] OAuth Client 的凭据通过安全渠道交付；没有被提交到代码库、配置样例或日志。
- [ ] 调用方确认 Client Credentials 的实际签发 scope 包含 `audit.ingest`。
- [ ] 调用地址使用正确的根路径：OAuth 地址不带 `/api/v1`，审计 API 带 `/api/v1`。
- [ ] 调用方具备持久化稳定 `event_id` 的能力，网络重试不会重新编号。
- [ ] `traceparent`、`X-Request-ID`、`X-Correlation-ID` 已按格式生成且不含敏感信息。

### 7.2 审计接口联调时

- [ ] 单条请求正文与请求头三元组完全一致。
- [ ] 批量请求中每条业务事件保留自己的原始三元组，不把整次投递头覆盖到所有事件。
- [ ] 批量 `events` 数量不超过 100，整个 Body 不超过 256 KiB。
- [ ] 只提交 `AuditEventInput` 已声明字段；不提交 `tenant_id`、`client_id`、密码、Token、Cookie 或原始请求/响应。
- [ ] `application_code`、`environment_code` 与 Token 绑定值完全一致。
- [ ] 把 `202 + DUPLICATE` 处理为幂等成功。
- [ ] 对所有失败响应记录 HTTP 状态、`code`（如有）、`request_id` 与本地 `event_id`，但不记录敏感凭据。

### 7.3 控制面接口联调时

- [ ] 先确认该接口是 Cookie 会话接口还是 OAuth/OIDC 协议接口，不混用认证格式。
- [ ] 根据 `router.go` 和 OpenAPI 确认所需权限码以及是否要求 MFA Step-Up。
- [ ] 对更新类请求使用服务端返回的最新 `version`。
- [ ] 对分页接口按对应 Schema 传递 `page`、`page_size` 和已定义筛选参数，不臆造新的查询字段。
- [ ] 对文件下载按文件流处理，不按 JSON 信封解析。
