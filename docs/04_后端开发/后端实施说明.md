## MFA 登录强制与高风险操作二次验证

- `000023_create_mfa_login_pre_auth.sql` 新增一次性登录预认证记录，仅持久化凭据摘要、尝试次数、过期时间和消费状态；原始预认证凭据只在密码校验成功的响应中返回，绝不写入日志、审计或浏览器持久化存储。
- `000024_create_mfa_step_up_grant.sql` 新增会话绑定的高风险授权记录。授权同时绑定租户、账号、会话和 MFA 因子挑战，最长有效期两分钟，目标接口消费后立即失效。
- 受保护的高风险路由固定先执行 `RequirePermission`，再执行 `RequireMFAStepUp`；没有权限的请求不会消耗二次验证授权。具体接口和请求头以[平台接口规范](../03_接口规范/平台接口规范.yaml)的 `x-mfa-step-up` 与 `X-MFA-Step-Up-Grant` 为准。

## 钉钉第三方企业应用扫码登录：契约与落地边界

钉钉扫码登录的 API 和数据安全契约已经写入[平台接口规范](../03_接口规范/平台接口规范.yaml)与[钉钉第三方企业应用扫码登录开发说明](../05_能力模块/钉钉第三方企业应用扫码登录开发说明.md)。它使用 `DINGTALK_QR` 独立提供商类型、MySQL 一次性扫码状态、预绑定外部身份哈希和既有 MySQL 会话/MFA 服务；不得把钉钉适配为 OIDC，也不得把授权码、上游令牌、原始外部身份标识或 SuiteSecret/客户端密钥写入审计、日志、Cookie 或平台 JWT。

钉钉扫码运行时使用 Gin 路由、GORM 状态仓储、现有本地会话签发和生命周期审计。对外契约必须使用官方 DTFrameLogin SDK 的 `dingtalk_frame` 配置，不得返回旧式授权地址字段。创建接口返回 `session_id`、`expires_at` 与 `sdk_config:{client_id,redirect_uri,response_type:"code",scope,state,prompt?}`；state 仅返回发起浏览器，MySQL 只保存摘要及加密载荷。回调必须以 **303 See Other** 完成：普通成功到受限 `return_to`，MFA 到 `/login?dingtalk_mfa=1&return_to=...`，失败到 `/login?dingtalk_error=<稳定码>`；不得返回 HTML 或跨窗口消息桥接内容。扫码浏览器绑定 Cookie 固定 `SameSite=Lax`，平台会话/MFA Cookie 继续沿用既有配置。具体字段、错误码、Cookie 与前端校验要求以 `钉钉第三方企业应用扫码登录开发说明.md` 和 OpenAPI 为准。

## 1. 目标与边界

- 架构：Go 模块化单体，Gin + GORM + MySQL Driver，MySQL；不使用 Redis、消息队列或微服务。
- 当前实现：控制台密码登录和 JWT Cookie 会话、IAM、RBAC、授权检查、审计接收/查询/导出/归档/保留期清理/死信重放、配置命名空间与发布、登录策略、连续失败锁定、管理员解锁、风险事件处置、平台基础设置、站内信通知、业务字典、登录目标管理与安全跳转、本地文件和异步任务控制面，以及进程内 Trace/Metric/运行日志采集查询与告警执行；并提供接入应用、环境、OAuth Client、Scope、普通回调地址、独立登出后回调地址、客户端公钥及客户端密钥的受控生命周期管理。OAuth/OIDC 运行时已提供 Client Credentials、Authorization Code + PKCE、Refresh Token、撤销、Discovery、JWKS、UserInfo、RP-initiated Logout、`private_key_jwt`、PAR、签名 JAR 与浏览器会话同意接口。
- 本轮身份增强：外部身份提供商本地控制面和外部主体绑定、标准 OIDC 远程登录、钉钉第三方企业应用预绑定扫码登录、TOTP 因子/恢复码/挑战、授权同意记录、客户端公钥与独立登出后回调地址已实现。密码登录和外部登录 MFA 强制与高风险操作二次验证已落地。独立 Vue 同意页仍待实现；审计归档、应用遥测元数据、告警及可配置 IP/网络登录策略也仍为后续项。
- 不创建第二套业务用户、角色或审计模型；合同、项目、报销系统通过 API/SDK 接入，不直连平台表。

每个领域模块均采用 `domain`、`application`、`infrastructure`、`interfaces/http` 四层。HTTP 层只做协议转换与参数校验；应用层定义事务和用例；领域层不依赖 Gin、GORM、SQL 驱动或文件系统；基础设施实现仓储和外部适配。

### 后端 `.env` 约定

- 项目根目录 `.env` 是后端及后续接入系统复用的本地运行配置入口；`backend/` 下启动的命令会在本地 `.env` 缺失时回退读取该文件，也可通过 `ENV_FILE` 指定其他路径。
- 根目录 `.env.example` 是允许提交的共享模板；根目录 `.env` 必须被 Git 忽略并仅限本地保存，不能写入真实密码、Token、私钥或生产配置。
- 系统环境变量优先级高于 `.env`，以便容器、CI/CD 和各接入系统安全覆盖配置。变量按 `APP_`、`MYSQL_`、`AUTH_`、`FILE_`、`LOG_`、`OTEL_` 等前缀划分，新增共享变量必须使用明确前缀。
- Vue/Vite 不读取根目录 `.env`；前端仅在 `frontend/.env.local` 中使用非敏感 `VITE_*` 变量。任何认证密钥、数据库密码和服务端 Token 均不得使用 `VITE_*` 前缀。
- 相对路径以所加载 `.env` 所在目录为基准。开发环境可从项目根目录运行 `make -C backend generate-dev-jwt-keys`，在根目录 `data/keys/` 下生成本地密钥，并在根目录 `.env` 配置对应路径；密钥目录不得提交。
- P7 新增 `AUTH_APPLICATION_JWT_AUDIENCE`、`AUDIT_APPLICATION_CODE`、`AUDIT_ENVIRONMENT_CODE`、`ASYNC_WORKER_ID`、`ASYNC_WORKER_POLL_INTERVAL`、`ASYNC_WORKER_STALE_LOCK_TIMEOUT` 和 `FILE_STORAGE_ROOT`。部署时需要分别启动 API 与 `make -C backend run-worker`；OAuth 客户端及其凭据由受控初始化/管理流程创建，不能在代码或 `.env` 中写入真实客户端密钥。

当前 Gin 请求链为：`Request ID → Recover → Access Log → CORS/Security Headers → Authentication → AuditTrail → Route Authorization → Validation → Application Service`。审计查询接口额外使用进程内固定窗口限流；不使用 Redis。认证中间件将 `Principal{tenant,user,account,session_id,roles,permission_codes}` 写入 `context.Context`，业务代码不得自行读取认证 Header/Cookie。

## 3. 认证、会话与权限

### 3.1 控制台登录

- `POST /api/v1/auth/login` 仅接受 `login_type=password`、账号和密码；密码凭据采用 Argon2id 校验。
- 校验成功后创建 `iam_session`，返回 `Set-Cookie: bp_session=<JWT>`；JWT 至少携带 `sid`、`sub`、`tid`、`aid`、`iat`、`exp`、`iss`、`aud`。
- Cookie 必须为 `HttpOnly`、`Secure`（开发环境可配置关闭）、`SameSite=Lax`、`Path=/`；浏览器端不保存 access/refresh token。
- 每个受保护请求都需校验 JWT、会话状态、过期时间、账号状态和租户一致性。刷新、退出和会话撤销必须同步更新 `iam_session`。
- `/api/v1/applications`、`/api/v1/oauth-clients` 已提供受 RBAC 与审计保护的接入登记、客户端密钥生命周期、独立登出后回调地址及客户端公钥管理；密钥明文只在创建或轮换时返回一次，响应包含 `Cache-Control: no-store`。根路径协议端点已支持 Client Credentials、Authorization Code + PKCE、Refresh Token、RFC 7009 撤销、Discovery、JWKS、UserInfo、RP-initiated Logout、`private_key_jwt`、PAR、签名 JAR 和浏览器会话同意接口。

### 3.2 权限原则

- 权限编码为 `{application}:{resource}:{action}`；菜单可见性不等于后端授权。
- 所有写操作按资源权限执行，并记录审计事件；高风险写操作在权限校验成功后必须消费会话绑定的一次性 MFA Step-up 授权。
- `authz_policy_revision` 变更后更新进程内权限缓存版本；不使用 Redis。

## 4. P0 数据模型映射

| 能力 | P0 主表 | 后端职责 |
|---|---|---|
| 租户与应用 | `iam_tenant`、`platform_application`、`platform_application_environment`、`platform_application_login_target` | 默认租户解析、应用/环境隔离，以及仅内部使用的登录目标精确解析 |
| 登录身份 | `iam_user`、`iam_account`、`iam_password_credential`、`iam_session` | 账号认证、禁用与会话撤销 |
| 组织任职 | `iam_org_unit`、`iam_position`、`iam_membership` | 主组织、兼岗、历史任职 |
| 授权 | `authz_resource`、`authz_permission`、`authz_role`、`authz_role_permission`、`authz_role_binding`、`authz_policy_revision` | 角色绑定和决策 |
| 审计 | `audit_event_dedup`、`audit_event`、`audit_ingestion_receipt` | 单条/批量幂等接收、批次投递回执、查询、受控导出 |
| 配置 | `cfg_namespace`、`cfg_item`、`cfg_release`、`cfg_release_item` | 命名空间、版本发布与读取 |
| 平台设置 | `platform_setting`、`notification_setting` | 机构资料、站内信偏好和历史兼容字段；不启用邮件发送 |
| 业务字典 | `dict_dictionary`、`dict_item` | 字典、字典项启停及运行时只读查询 |
| 异步任务 | `async_job` | 导出、归档等可重试后台任务 |

所有聚合根使用 ULID、`tenant_id`、`status`、`version`、UTC `DATETIME(3)` 和创建/更新人字段。审计事件保留内部 `subject`、`request_id`、`trace_id`、`correlation_id`，但当前控制台列表、详情和导出 DTO 不对外返回这些关联字段。批量投递回执单独保存于 `audit_ingestion_receipt`，不得覆盖事件原始业务关联三元组。

## 6. 审计与异步原则

- `AuditTrail` 自动记录已认证的 P0 写操作，以及审计查询、导出任务创建和下载访问；它只记录固定的资源、结果、Request ID、来源 IP 等摘要，不读取请求体或响应体。密码创建、初始化、管理员重置和自主修改均受该规则约束，任何明文密码（包括仅在重置成功响应中短暂返回的 `temporary_password`）不得进入审计、日志或持久化字段。成功登录、成功退出、已识别账号的登录失败和锁定会以可信身份上下文最佳努力写入生命周期审计；未知账号失败不关联账户身份。首个超级管理员初始化不依赖认证会话，成功后以 `SYSTEM/bootstrap` 最佳努力写入高风险审计，元数据不得包含初始化令牌或密码。
- 接入系统应先在本地事务写 `audit_outbox`，再用 `POST /oauth2/token` 获取携带 `audit.ingest` 范围的应用 Bearer 令牌，调用单条或批量审计接收接口。应用 JWT 使用 Ed25519 `EdDSA` 验签，并在每次调用时以数据库当前启用的 OAuth Client、Application、Environment 和 scope 复核令牌绑定；令牌中绑定的 tenant、application、environment 是接收边界，调用方不得覆盖。外部审计 JSON 不接受 `client_id`，服务端只从可信应用主体注入该内部字段。
- 审计事件不可通过业务 API 删除。导出请求创建 `async_job` 的 `PENDING` 记录；独立 Worker 以 MySQL 行锁领取、失败重试并生成本地 CSV，成功任务可通过租户/权限校验后的下载接口读取。归档、保留和过期清理仍为 P1。
- “审计上报重试”仅重放平台接收侧死信或失败任务，不得越权操作外部业务系统的本地 Outbox。

### 6.1 跨应用登录与批量审计接收的当前实现边界

- `platform_application_login_target` 已由迁移 `000027_create_application_login_target.sql` 建表，当前仅实现服务内按 `(tenant_id, application_id, environment_id, target_code)` 精确解析 `ACTIVE` 目标。没有登录目标管理、解析或浏览器跳转 HTTP 接口，OIDC `/authorize` 也不接收 `target_code`。
- `000028_add_audit_correlation_id.sql` 已为 `audit_event` 增加业务 `correlation_id`。单条审计上报要求事件体三元组与 HTTP 头三元组一致；批量上报中，请求头三元组属于一次 Outbox 投递，事件体三元组仍是各自原始业务链路。
- `000029_create_audit_ingestion_receipt.sql` 已建立批次投递回执表。批量服务先验证全部事件，再在一个 GORM 事务中写入事件/去重结果和状态为 `COMPLETED` 的回执；回执记录事件总数、接收数和重复数。校验或存储失败会整体回滚，不产生部分写入或回执；重复事件是成功的逐项 `DUPLICATE`。

## 7. 实施验收

- 已实现的业务 API 位于 `/api/v1`，并复用统一的成功/失败响应、严格 JSON 解码和分页参数约定；标准 OAuth/OIDC 根路径端点包括 `GET /authorize`、`POST /oauth2/token`、`POST /oauth2/par`、`POST /oauth2/revoke`、`GET|POST|DELETE /oauth2/consent`、`GET /.well-known/openid-configuration`、`GET /oauth2/jwks`、`GET|POST /oauth2/userinfo` 与 `GET|POST /oauth2/logout`，响应不套业务信封。协议运行时还包括 `private_key_jwt`、签名 JAR 与专用 post-logout URI 校验。
- 用户、账号、任职、配置项、平台设置、通知设置、字典和字典项更新均验证租户与 `version`；资源、角色、角色绑定、配置发布及字典写入使用显式 GORM 事务或冲突检查，鉴权由 Gin 路由的声明权限强制执行。
- 审计接收按 `event_id` 幂等，敏感元数据和变更摘要递归脱敏；审计事件没有删除路由。所有列表遵循 `page`、`page_size`、`keyword`、`filter[...]` 格式。
- 没有 Redis 依赖；限流使用进程内固定窗口；审计导出文件仅保存到 `FILE_STORAGE_ROOT`，由 API 下载接口流式输出；实际运行日志与 OTel 数据不进入业务 MySQL。
- 已完成当前代码库的 `go test ./...`、`go vet ./...` 和差异格式检查；真实 MySQL 迁移、事务回滚、锁和跨进程并发仍必须在隔离验收数据库验证，默认不会连接或修改本地 `.env` 指向的数据库。
