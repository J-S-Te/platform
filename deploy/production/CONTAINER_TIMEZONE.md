# 离线服务器显示时区配置

> 2026-10-13 当前工作区源码核验；未运行新的部署或动态验收。


此工具只配置应用的本地显示时区，不修改宿主机时钟、DSN、数据库会话或历史记录。授权和 Token 仍按绝对时间判断。UTC 显示与北京时间相差八小时不代表时钟不准。

## 操作

先通过受控发布交付本版脚本资产及支持时区覆盖层的新版 subsystem-provisioner。不能只复制脚本到旧控制面：旧部署器可能在后续子系统更新时丢失覆盖配置。这里的源码构建和替身回归不代表客户镜像已经发布。

在已配置部署目录中执行：

```bash
sudo bash bin/set-container-timezone.sh check
sudo bash bin/set-container-timezone.sh configure --tz Asia/Shanghai
sudo bash bin/set-container-timezone.sh apply
```

默认只选择当前运行的非数据库服务；首次安装前可以重复使用 `--service 服务名` 选择本机已导入镜像的服务。apply 不会启动原本停止的服务。缺时区数据、镜像或工具时先通过受控离线包补齐；工具不安装依赖、不联网拉取或构建镜像。检查阶段可能使用本地镜像启动无网络的一次性 `test` 进程，仅用于读取 zoneinfo，不启动业务入口。

配置仅生成 `runtime/compose.timezone.yaml`（JSON 是合法 YAML），原 Compose、`.env`、`.release.env`、runtime 凭据、DSN 均不改写。覆盖层位于现有共享 runtime 挂载内，发布脚本及平台受控部署器均能读取，不需要挂载新文件。文件0600，备份位于 `runtime/timezone-backup.*`，包含敏感配置，不可提交或随客户包二次分发。不要绕过包装入口使用裸 Compose。

数据库服务明确排除：改变 MySQL SYSTEM 时区可能改变 NOW()/TIMESTAMP 语义。已有混合时间数据、历史 UTC DATETIME 或时区错误需要单独核对、迁移及回归，不能统一加八小时。`--shift-history`、`--recreate` 已移除；`--check-only` 兼容只读检查。

## 校时与离线边界

有内网 NTP 时由管理员配置内网时间源；完全隔离时人工核对系统及 RTC 时间。没有时间源会报告“时间准确性未确认”，不阻止单纯显示配置。脚本不调用 `date -s` 或修改时间同步策略。校准若涉及时间回拨，应按商业授权签名恢复流程评估，不能绕过保护。

## 应用及恢复

apply 委托 `deploy.sh timezone-apply`，共用 `runtime/.deploy.lock`。只处理当前已运行且配置镜像与实际镜像一致的单副本服务；固定实际镜像 ID，禁止 pull/build，检查依赖并按顺序等待健康。存在控制面升级门禁时应先完成既有受控恢复流程。

失败时尝试恢复本轮已处理容器的原 TZ/Java 显示配置。目标覆盖层保留，不宣称业务事务回滚；恢复失败须停止发布并人工处理。重新执行 check，再决定重试。若要撤销配置，持部署锁将备份覆盖层恢复（首次配置可移走新覆盖层），再通过受控维护流程恢复服务。不得删除数据库卷、授权状态或运行凭据。

SIGKILL、主机断电无法由 shell trap 自动恢复。恢复后必须核对覆盖层、当前运行服务及备份，不能假定容器已经一致。

## 验收

原生回归：`bash bin/test-container-timezone.sh` 使用临时配置与 Docker 替身，不接触实际容器。它只证明脚本契约，不等于真实离线安装通过。

发布前在一次性隔离 Docker 安装中验证断网应用、UTC/上海宿主机、重启及依赖失败；对照同一记录的授权到期、会话有效期、审批、审计与任务调度绝对时间不变。显示配置完成不等于这些业务验收完成。

## 2026-10-13 操作核验补充

执行人须为持部署目录及 Docker 权限的运维，并已获准重建所选运行服务；本次没有执行此工具或真实容器验收。
默认目录不适用时三阶段命令都显式传 --dir <实际部署根>，先 check，再 configure，最后获批 apply。
configure 生成覆盖层和备份；check 也可能创建隔离一次性测试容器／临时文件，不是零运行态操作。
apply 仅重建当前运行、单副本且镜像配置与实际一致的非数据库服务；不补齐原本停止的服务，不导入镜像、不迁移数据库。
任何 pending 控制面／资产事务须先按绑定制品流程完成，不能删门禁来应用时区。

成功判据是所选服务健康、显示时区符合批准值，随后由业务负责人复核绝对时间及调度。
失败恢复只是原 TZ／Java 显示配置和容器的尝试，不回滚业务事务；失败后保留覆盖层和备份，核对实际容器再决定重试。
