# 离线与 CI/CD 部署兼容契约

> 2026-10-22 当前工作区源码核对；下文带日期的验证保留原范围，本轮未运行部署或动态验收。

## 当前登记与发布完整性边界

商业JWS/签名快照仍为协议1；内置目录版本1，组件登记V2与V1桥接独立。普通V2镜像更新保持实例/应用/环境/服务/凭据代次身份；V1镜像批准、旧安装证据和四系统发布器按限定入口保留，不能互相替代。API/Agent/消费者的目录和协议支持必须配套升级。

离线正式签名交付在介质脚本执行前使用介质外可信verifier/trust；统一结构检查不验证这一信任链。CI/CD及离线都应核对实际发行资产，不以源码文件存在推断已交付。统一入口参数与恢复见 [DELIVERY_WORKFLOW.md](DELIVERY_WORKFLOW.md)。

## 2026-10-15 离线契约补充

公共代理镜像只从固定 GHCR 摘要取得，运输 tag 保持兼容旧导入器。新版公共包记录成对上游来源与归档 config digest，导入后通过本地 Registry 不可变引用交付；平台、File Gateway 和代理的 release 指针同事务提交。Compose 禁止自动拉取；离线缓存缺失在停止平台前失败。旧包没有新来源记录时不会被当作新版固定镜像，也不自动重写旧包 SHA256。

生产 CRM 为九消费者，包含独立许可与状态卷的转合同 Worker。运行、停用和 shell 验收从审核 profile 取得服务集合；合同共享库及 Temporal 保留。验收同时核对实际镜像、必需进程健康/稳定性及正常平台状态处理器给出的 READY/已验证清单，任一失败保留候选。此检查需要新版平台 `license-install verify-deployment` 二进制，资产升级须配合平台协调升级。

售前 Temporal Build ID 从不可变 CRM digest 派生，与镜像指针一起暂存、一起回退。full/shared 构建输入共用 `offline-build-inputs.sh`，包括内嵌平台授权库及其同步校验；旧增量基线不能跳过新的兼容性锁。服务器预检读取实际 image store 和 containerd 有效 root，合并同分区预算；不移动 Docker/containerd 数据。

隔离工具/事务/协议回归记录在工程 `.ai/qa/offline-delivery-fixes-20261015/`。这些验证不代替四系统真实断网安装、转合同业务交付、到期暂停/续期恢复与自然 ACK 验收。


离线交付和 CI/CD 是同一生产运行模型的两种制品传输方式，不是两套业务部署。两者必须使用相同的源码、Dockerfile target、Compose 服务定义、迁移二进制、运行时配置键、健康检查与应用接入状态机。

## 唯一允许变化的部署环节

| 能力 | CI/CD | 离线部署 |
| --- | --- | --- |
| 制品交付 | 推送 OCI 镜像并按 `image@sha256:digest` 拉取 | 传递校验过的镜像归档，导入本机 Registry，并按 `image@sha256:digest` 引用 |
| 运行配置 | 由部署 Secret/受限运行时文件注入 | 由一次性配置和平台受控接入写入相同运行时文件 |
| 发布执行 | `deploy-service.sh` 执行备份、迁移、重建、健康检查 | 相同脚本和生产 Compose 执行同一流程 |
| 子系统接入 | 平台应用接入状态机 | 同一平台状态机；普通离线导入后准备候选镜像，不绕过采用；审核授权安装计划可自动调用受控采用流程 |

业务代码禁止根据“离线包/CI/CD”切换业务规则、默认授权、租户范围或失败安全策略。部署差异只能通过显式配置和依赖可用性表达；生产下的缺密钥、依赖不可用、迁移失败及健康检查失败必须一致地 fail closed。

## 业务层兼容要求

- API、Worker、迁移器必须来自同一应用源码版本；一个服务有多个 Docker target 时，两种发布都要提供每个 target 的独立不可变摘要。
- 环境变量名、必填条件、默认值和安全校验由应用定义。CI Secrets 与离线运行文件只是不同的注入来源，不得把 Secret 烘焙进镜像或记录进镜像标签。
- 迁移须版本化、可重放校验、具备数据库锁；各应用迁移责任须按真实启动链路核对；File Gateway 在独立进程启动时执行版本化文件迁移，不能把它写成完全不执行启动迁移。迁移完成但服务不健康时，部署器必须保留迁移事实并按实际入口的回退能力处理运行镜像，不得声称数据库已回滚。
- OIDC 公网 Issuer、回调 URL 与内部服务地址必须使用各自明确配置；离线网络不能把公网 Issuer 错误替换为容器 DNS，也不能让业务信任未经验证的请求 Host。
- 文件、数据库、密钥与审计数据使用相同的持久化及备份策略；离线升级不能因镜像重新导入而覆盖运行配置或持久卷。
- 异步任务要有幂等键、可重试错误边界和启动 readiness；外部依赖不可达时只能进入可观测的未就绪/重试状态，不能伪报业务成功。
- 真正的用户业务离线能力（例如现场采集后补传）与“服务器通过离线包安装”不同，必须各自定义业务冲突解决、幂等和数据保护规则。

## 发布门禁

平台 CI 验证发布脚本、离线包清单与部署状态机；各子系统 CI 验证对应镜像 target、迁移和 readiness。离线包生成必须覆盖同一应用 CI 发布使用的所有运行 target。导入后每个 Compose service 都须使用其匹配的不可变 digest，并通过同一套备份/迁移/健康检查流程。

回归脚本：`bin/test-deployment-parity.sh`。它针对数据看板 API、聚合 Worker、告警 Worker、迁移器校验离线包和 CI/CD target 对齐，并验证离线导入后 `.release.env` 中的四个独立摘要不会被折叠成单一镜像。

由发布负责人同时核对离线包与 CI 工作流；本次未运行 parity 或真实部署。
同一运行模型是兼容目标，不代表两种资产打包列表已完全相同。
当前 platform/.github/workflows/ci-cd.yml 的 tar 白名单未列入 CONTAINER_TIMEZONE.md，
而离线资产路径已交付该说明；应在正式交付前对照包目录，不把源码存在当作 CI 已同步。
此项仅文档记录，未修改工作流。

test-deployment-parity.sh 只覆盖数据分析四 target／release 摘要契约，不证明全部六系统端到端兼容。
平台需平台／网关两个摘要，数据分析需四 target 摘要；子系统不因运输方式变化而共享浏览器／机器凭据。
Shell 发布具备对应镜像／指针回退分支，但生产 Agent 更新不存在统一保证的全流程自动回滚；
两者均不能自动逆转 SQL 迁移。失败需记录已迁移事实并选择经审批的恢复路径。

生产脚本使用相同统一发布锁、受控清单和数据库备份门禁；时区覆盖须由新版包装入口与 Agent 一起读取。
恢复和业务验收以 [BACKUP_RECOVERY](BACKUP_RECOVERY.md) 及 [ACCEPTANCE_CHECKLIST](ACCEPTANCE_CHECKLIST.md) 为准。
