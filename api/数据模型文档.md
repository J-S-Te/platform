# Basic-Platform 数据模型文档（当前实现）

> **用途**：供后端开发、数据库评审与联调使用。本文只整理仓库中已经提交的 MySQL 迁移与当前后端代码可直接确认的内容；需求变化必须先通过迁移、代码与测试形成可核对的事实。
> **代码基线**：仓库当前工作区，迁移文件 `backend/migrations/000001` 至 `000031`。
> **生成日期**：2026-07-21。

## 1. 范围与阅读规则

1. **数据库结构以迁移为准**：本文件的字段、类型、键和外键来自 `backend/migrations/*.sql`，不是根据 DTO 或前端字段反推。
2. **接口对象不等于数据库行**：HTTP 响应会掩码敏感数据、合并关联对象或转换字段名；请同时查阅同目录的《接口文档》。
3. **枚举值不在本文臆测**：许多 `status`、`type`、`risk_level` 等列在 MySQL 中是 `VARCHAR`。除非当前代码的校验逻辑直接限定了取值，否则本文不自行补充候选值。
4. **迁移可追溯**：每张由迁移创建的表章节均列出首次定义它的迁移文件；`000025` 为联邦身份提供商表增加运行时配置列，`000030` 又调整其 `issuer` 的可空性，`000031` 创建钉钉扫码一次性状态表；相关变更均在本文说明。
5. **运行时代码与迁移不一致时单独标记**：如后续发现代码引用的表在迁移中没有定义，只记录已确认的代码映射，不伪造列类型、索引或外键。本版本的钉钉扫码状态表已有 `000031` 迁移，不属于此类。

## 2. 存储约定（可由迁移直接确认）

- 所有建表语句使用 `ENGINE=InnoDB`、`DEFAULT CHARSET=utf8mb4`、`COLLATE=utf8mb4_unicode_ci`；需要精确二进制比较的 ID、代码等列会显式指定 `ascii_bin` 或 `utf8mb4_bin`。
- 大多数主实体主键为 `CHAR(26)`（ASCII 二进制排序）；关联表或快照表也存在复合主键。不要把主键强制当成整数处理。
- 大多数可管理实体带有 `version BIGINT UNSIGNED`，用于当前代码中的乐观并发控制；写接口通常会携带 `version`。
- `created_at`、`updated_at` 等时间列使用 `DATETIME(3)`；OAuth/OIDC、会话与审计表另外有过期、撤销、消费等生命周期时间列。
- `JSON`、`TEXT`、`BLOB` 和二进制摘要列必须按其实际存储语义处理，不能假定都可作为普通字符串返回。

## 4. 可直接确认的敏感数据与凭据存储边界

以下结论来自表字段和迁移注释；它们是后端实现与排障时必须遵守的边界。

| 数据类别 | 相关字段 / 表 | 迁移中可确认的存储方式 |
|---|---|---|
| 手机号 | `iam_user.mobile_ciphertext`、`iam_user.mobile_hash` | 密文和固定长度哈希分列保存；没有明文手机号列。 |
| 本地密码 | `iam_password_credential.password_hash`、`hash_algorithm`、`algorithm_params` | 保存密码摘要、算法与参数；没有明文密码列。 |
| 控制台会话刷新令牌 | `iam_session.refresh_token_hash` | 仅保存刷新令牌摘要。 |
| OAuth 客户端密钥 | `platform_oauth_client_credential.secret_hash` | 保存客户端密钥摘要；公钥凭据另存 `public_key_jwk`。 |
| OIDC 授权码 / 刷新令牌 | `oauth_authorization_code.code_hash`、`oauth_refresh_token.token_hash` | 保存摘要并有消费/撤销等状态字段。 |
| MFA TOTP、恢复码、挑战 | `iam_mfa_totp_factor.secret_ciphertext`、`iam_mfa_recovery_code.code_hash`、`iam_mfa_challenge.challenge_hash` | TOTP 密文；恢复码与挑战使用哈希。 |
| 登录前置验证与高风险授权 | `iam_mfa_login_pre_auth.credential_hash`、`sec_mfa_step_up_grant.challenge_hash`、`grant_hash` | 原始凭据/授权值不作为普通列保存。 |
| 联邦提供商密钥及登录状态 | `iam_federated_identity_provider.client_secret_ciphertext`、`iam_federated_login_state.state_hash`、`payload_ciphertext` | 客户端密钥、临时登录载荷采用密文或哈希字段。领域模型进一步规定：`DINGTALK_QR` 的当前管理 HTTP 字段为 `client_id` / `client_secret`；第三方企业应用（ISV）内嵌二维码场景中，它们分别承载钉钉 `SuiteKey` 与 `SuiteSecret`/客户端密钥。`app_key` / `app_secret` 仅为兼容性术语，不是当前 HTTP JSON 字段；数据库分别使用 `client_id` 与密文字段保存应用标识和加密秘密。明文密钥不会由管理 HTTP 适配器序列化，也不应写入应用日志。 |
| 审计事件完整载荷摘要 | `audit_event.payload_hash` | 保存 SHA-256 摘要；`metadata`、`changes` 为 JSON 列，写入时由审计仓储进行敏感字段脱敏。 |

## 5. 可由外键确认的关系原则

- `iam_tenant` 是多个业务表的显式外键目标；业务实体均以 `tenant_id` 约束租户边界。
- `platform_application` 关联租户，`platform_application_environment` 关联应用；OAuth 客户端再关联应用与环境。
- 用户、账号、组织、岗位、任职、角色绑定、MFA、会话、审计与配置表通过显式外键或复合键连接。
- 审计事件主表为了写入与分区需要，键设计与一般业务表不同：`audit_event` 以 `(id, occurred_month)` 为主键，去重表 `audit_event_dedup` 保存应用事件 ID 到审计行的映射。
- `ON DELETE RESTRICT` 是迁移中大量外键采用的策略；业务删除/停用流程不能假设数据库会级联删除关联记录。

### `iam_dingtalk_qr_login_state`

来源：`backend/migrations/000031_create_dingtalk_qr_login_state.sql`。

该表已由迁移创建，用于钉钉第三方企业应用扫码的短时、一次性 state。原始 state、浏览器绑定值、授权码、SuiteSecret/客户端密钥、上游访问令牌及钉钉身份标识绝不入库；钉钉原始 `unionId` 亦不存不记。

| 列 | 迁移中的列定义 | 已确认用途 |
|---|---|---|
| `id` | `CHAR(26) CHARACTER SET ascii COLLATE ascii_bin NOT NULL` | 状态记录标识。 |
| `tenant_id` | `CHAR(26) CHARACTER SET ascii COLLATE ascii_bin NOT NULL` | 租户归属。 |
| `provider_code` | `VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL` | `DINGTALK_QR` 提供商代码。 |
| `state_hash` | `BINARY(32) NOT NULL` | 浏览器回调 state 的 SHA-256 摘要；state 原文不入库。 |
| `payload_ciphertext` | `BLOB NOT NULL` | 受 `IAM_EXTERNAL_LOGIN_STATE_ENCRYPTION_KEY` 保护的服务端私有载荷；包含浏览器绑定哈希、会话 ID、提供商 ID/SuiteKey、回调地址与受限 `return_to`，不包含原始浏览器绑定值或 state。 |
| `created_at` | `DATETIME(3) NOT NULL` | 创建时间。 |
| `expires_at` | `DATETIME(3) NOT NULL` | 一次性扫码状态过期时间。 |
| `consumed_at` | `DATETIME(3) NULL` | 被消费或判定过期的时间。 |
| `status` | `VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NOT NULL` | 运行时仅写入 `ACTIVE`、`CONSUMED`、`EXPIRED`。 |

**键、索引与外键（原始迁移定义）**

- `PRIMARY KEY (id)`。
- `UNIQUE KEY uk_dingtalk_qr_login_state_hash (state_hash)`，保证同一 state 摘要不可重复。
- `KEY idx_dingtalk_qr_login_state_expiry (status, expires_at)`，支持过期状态查询与清理。
- `KEY idx_dingtalk_qr_login_state_tenant_provider (tenant_id, provider_code, status, expires_at)`，支持租户/提供商边界内的状态查询。
- `fk_dingtalk_qr_login_state_tenant`：`tenant_id -> iam_tenant(id)`，`ON DELETE RESTRICT`。
- `fk_dingtalk_qr_login_state_provider`：`(tenant_id, provider_code) -> iam_federated_identity_provider(tenant_id, provider_code)`，`ON DELETE RESTRICT`。

**运行时消费边界**

- 创建接口把 state 原文仅返回给发起浏览器的 `sdk_config.state`；数据库仅存 `state_hash` 和加密载荷。加密载荷可承载浏览器绑定哈希、会话 ID、提供商上下文、回调地址和受限 `return_to`，不保存原始浏览器绑定值。
- 回调在事务中以 `SELECT ... FOR UPDATE` 锁定 state 摘要对应行；非活动、已过期或并发重复消费均为无效。有效记录先不可逆更新为已消费，再执行钉钉身份换取及本地预绑定检查。
- 回调必须先验证浏览器绑定，再原子消费 state。浏览器绑定不匹配时拒绝当前请求但不消费 state；通过绑定校验后 state 只能消费一次，即使钉钉身份校验、账号检查或 MFA 后续处理失败，也不得重放。扫码浏览器绑定 Cookie 固定 `SameSite=Lax`，不在此表保存。
- 已超过 `expires_at` 的 `ACTIVE` 记录由消费事务改写为 `EXPIRED` 并写入 `consumed_at`；正常消费改写为 `CONSUMED` 并写入 `consumed_at`。因此 `consumed_at` 表示“已成功消费或已被判定过期”，不是登录成功时间。
- 钉钉稳定身份仅以现有外部身份绑定记录的 `subject_hash` 参与 `(tenant_id, provider_code, subject_hash)` 查找；原始 `unionId` 只在进程中立即哈希，绝不写入本表、外部身份绑定表、审计详情或运行日志。
- 审计不从本表复制协议敏感值。可建立 tenant/provider 生命周期上下文时，分别记录 `auth.dingtalk_qr_session.create`、`auth.dingtalk_qr_callback` 与（预绑定成功时）`auth.dingtalk_qr_binding`；缺少可信上下文的早期回调拒绝仅记录安全日志。

**当前领域层可确认的类型语义**

- 支持的提供商类型常量为 `OIDC` 和 `DINGTALK_QR`。`OIDC` 配置要求有效的 issuer、回调地址及包含 `openid` 的 scope；`DINGTALK_QR` 不使用 OIDC issuer，应用层要求 `issuer` 为空、回调地址为 HTTPS，且至少显式配置一项钉钉上游权限（不要求 `openid`）。
- 对 `DINGTALK_QR`，当前管理接口使用 `client_id` / `client_secret` 字段；第三方企业应用（ISV）内嵌二维码场景中，二者分别映射为钉钉 `SuiteKey` 与 `SuiteSecret`/客户端密钥。`app_key` / `app_secret` 只保留为跨系统沟通的兼容性术语，当前 Gin HTTP 请求不接受这两个 JSON 字段；读取响应也只给出 `client_secret_configured`，不回传秘密。数据库以 `client_id` 保存 SuiteKey，并以 `client_secret_ciphertext` 保存应用层加密后的 SuiteSecret/客户端密钥。第三方企业应用必须使用钉钉开放平台当前控制台为该应用发放的对应凭据，不得与企业内部应用凭据混用。数据库迁移只定义列类型；该语义来自 `identity/federation/domain/model.go`，不可泛化到其他提供商类型。
- 联邦绑定表只保存 `subject_hash`；领域模型明确禁止把上游原始 subject 放入聚合、接口响应、日志或持久化模型。

## 9. 迁移与发布核对

- 迁移执行器使用 `platform_schema_migration` 保存 `version`、`name`、`checksum`、`applied_at`；该表由 `backend/internal/migration/migration.go` 在运行时保证存在。
- 迁移按版本号顺序执行，并对已执行迁移的 SHA-256 校验和进行比对；校验和不一致会被视为迁移错误。
- 迁移源代码明确不使用 GORM `AutoMigrate` 维护生产模式的 schema history。因此新增表/列/索引应通过新的、可评审的 SQL 迁移完成。
