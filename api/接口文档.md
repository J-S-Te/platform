# Basic-Platform 接口文档（当前实现）

> **用途**：提供给后端开发与调用方进行真实接口对接。  
> **范围**：路由以 `backend/internal/transport/http/router.go` 为准；请求/响应字段以各模块 `interfaces/http` 适配器为准。  
> **生成日期**：2026-07-21。本文不把旧设计稿、前端 mock 或未注册路由写成可调用接口。

## 1. 总体约定

### 1.1 地址、格式与时间

- 控制台业务 API 的公共前缀是 `/api/v1`。
- 登录与 OIDC/OAuth 协议端点位于根路径，例如 `/api/v1/auth/login`、`/oauth2/token`、`/.well-known/openid-configuration`。
- 普通平台 API 使用 JSON；表单协议端点（OAuth/OIDC）使用 `application/x-www-form-urlencoded` 或查询参数，且**不使用**平台统一响应包裹。
- `time.Time` / 时间字符串字段由 Go JSON 编码输出为 RFC 3339 时间；本文不把它缩写成仅日期。

### 1.2 平台统一成功 / 失败响应

除 OAuth/OIDC 协议端点和文件下载外，HTTP 适配器通过以下包裹返回数据：

```json
{
  "code": "OK",
  "message": "操作成功",
  "request_id": "服务端请求 ID",
  "data": {}
}
```

```json
{
  "code": "PLATFORM_VALIDATION_ERROR",
  "message": "请求参数不合法",
  "request_id": "服务端请求 ID",
  "details": {}
}
```

当前共享错误码包括：

| HTTP 状态 | 错误码 | 场景 |
|---:|---|---|
| 401 | `AUTH_UNAUTHENTICATED` | 未登录、会话/JWT 无效或已过期。 |
| 403 | `AUTH_FORBIDDEN` | 已认证但缺少路由要求的权限。 |
| 404 | `PLATFORM_NOT_FOUND` | 路由或资源不可用。 |
| 405 | `PLATFORM_METHOD_NOT_ALLOWED` | 已知路由但方法不支持。 |
| 409 | `IAM_CONFLICT` / `IAM_VERSION_CONFLICT` | 业务状态冲突或乐观锁版本冲突。 |
| 422 | `PLATFORM_VALIDATION_ERROR` | JSON、表单或业务输入校验不通过。 |
| 500 | `PLATFORM_INTERNAL_ERROR` | 服务端已记录内部异常。 |
| 503 | `PLATFORM_DEPENDENCY_UNAVAILABLE` | 就绪检查发现依赖不可用。 |

MFA 二次验证还会使用：`AUTH_MFA_STEP_UP_REQUIRED`（403）、`AUTH_MFA_STEP_UP_EXPIRED`（410）、`AUTH_MFA_VERIFICATION_FAILED`（401）、`AUTH_MFA_ATTEMPTS_EXCEEDED`（401）。

### 1.3 控制台会话、应用 Bearer 与 MFA 二次验证

| 调用边界 | 认证方式 | 适用路由 |
|---|---|---|
| 控制台用户 | `AUTH_SESSION_COOKIE_NAME` 对应的 HttpOnly Cookie；默认配置名为 `bp_session` | 大多数 `/api/v1` 管理接口和 `/api/v1/auth` 的 refresh/logout/me。 |
| 外部应用接入 | `Authorization: Bearer <application access token>` | `POST /api/v1/audit/events` 与 `POST /api/v1/audit/events:batch`。还必须有 `audit.ingest` scope。 |
| 高风险管理操作 | 已登录 Cookie + `X-MFA-Step-Up-Grant: <one-time-grant>` | 路由表中标为“是”的操作。授权与当前 tenant/account/session 绑定，且由中间件消费一次。 |

**不能把浏览器会话 JWT 放进 `Authorization` 请求头替代 Cookie。** 当前 `Authentication` 中间件只读取配置的 session Cookie；应用 Bearer 认证只用于独立接入边界。

### 1.4 通用输入规则

- JSON 适配器普遍使用 `DisallowUnknownFields`，未知字段会导致 422；不要发送客户端私有字段。
- 多数写操作需要 `version` 以实施乐观锁；字段在 DTO 中出现并不表示可省略。
- `tenant_id`、审计人、创建人等不是控制台请求体字段，服务端从认证主体取得。
- 带 `*` 的字段在下面 DTO 目录中对应 Go 指针 / 可空响应值；这说明 JSON 适配器可以区分“未给出 / null”和零值，但最终必填性仍由当前业务用例校验决定。

## 3. OIDC / OAuth 协议端点

这些端点返回 OAuth/OIDC 规范风格的 JSON 或重定向，不使用 `code/message/request_id/data` 包裹。已注册端点如下：

| 方法与路径 | 主要输入 | 主要输出 / 说明 |
|---|---|---|
| `GET /authorize` | 查询参数：`response_type`、`client_id`、`redirect_uri`、`scope`、`state`、`nonce`、`code_challenge`、`code_challenge_method`、`request_uri` 等 | 当前处理 `response_type=code`；成功时按已验证 redirect URI 重定向。 |
| `POST /oauth2/token` | 表单 `grant_type`；支持 `authorization_code`、`refresh_token`、`client_credentials` | 返回 `access_token`、`token_type`、`expires_in`，并可返回 `refresh_token`、`id_token`、`scope`。客户端认证由 Basic 或受支持的表单字段处理。 |
| `POST /oauth2/par` | 表单授权请求 + 客户端认证 | 201：`request_uri`、`expires_in`。默认 PAR TTL 在 handler 中为 90 秒。 |
| `POST /oauth2/revoke` | 表单 `token`、可选 `token_type_hint` + 客户端认证 | 撤销处理；协议错误采用 OAuth error JSON。 |
| `GET /oauth2/consent` | 已认证浏览器会话及同意上下文 | 返回当前同意页面所需数据。 |
| `POST /oauth2/consent/grant` | 与 OIDC issuer 同源；已认证浏览器会话 | 提交授权同意。路由有 Same-Origin 防护。 |
| `DELETE /oauth2/consent` | 已认证浏览器会话 | 撤销用户同意。 |
| `GET /.well-known/openid-configuration` | 无 | OIDC discovery 文档。 |
| `GET /oauth2/jwks` | 无 | 当前 OIDC 签名公钥集合。 |
| `GET` / `POST /oauth2/userinfo` | Bearer access token | 返回 access token 对应用户信息；额外核对当前 client/session/subject 仍有效。 |
| `GET` / `POST /oauth2/logout` | 会话 / 协议参数 | 登出当前 OIDC 会话。 |

### 3.1 Token 与 PAR 的已确认表单约束

- `/oauth2/token` 拒绝 query string；同一表单字段不能重复。支持的 grant 值为 `authorization_code`、`refresh_token`、`client_credentials`。
- authorization-code 交换读取：`code`、`redirect_uri`、`code_verifier`；refresh 读取 `refresh_token`；两者都会走客户端认证。
- client-credentials 支持 `scope` 空格分隔输入；该流程产生应用 access token，详细 JWT 约束见《JWT文档》。
- `/oauth2/par` 仅接受 `response_type=code`；校验 `scope`、`state`（最大 2048）、`nonce`（最大 255）、redirect URI 的绝对性，以及 PKCE `code_challenge` / `code_challenge_method` 的成对出现。支持的方法是 `S256` 或 `plain`。

## 5. 外部系统审计接入接口

| 方法与路径 | 认证与 scope | 请求体 | 成功结果 |
|---|---|---|---|
| `POST /api/v1/audit/events` | `Authorization: Bearer` 应用 access token + `audit.ingest` | `eventInputPayload` | 事件接收回执。 |
| `POST /api/v1/audit/events:batch` | 同上 | `{ "events": [eventInputPayload] }` | 批量接收回执。 |

这两条 POST 路由与控制台审计查询使用不同认证中间件：外部系统没有控制台用户角色权限也能接入，但必须有应用 token 和 `audit.ingest` scope；反之，用户 Cookie 不能替代 Bearer token。

## 6. 对接检查清单

1. 控制台调用启用 cookie 凭据，不能自行读取或持久化 JWT。
2. 写接口先读取最新资源并原样提交 `version`；收到 409 后重新读取而不是盲目重试。
3. 高风险路由先完成 step-up challenge，再在**下一次**目标请求携带一次性 `X-MFA-Step-Up-Grant`。
4. OAuth/OIDC 客户端按协议格式处理错误（`error` / OAuth redirect），不要用平台错误包裹解析器处理。
5. 从所有响应记录 `request_id`，用于与服务端结构化日志、审计事件关联。
6. 密码、`client_secret`、MFA secret、恢复码、重置临时密码、step-up grant 都是敏感一次性值：禁止写日志、审计详情、浏览器持久化存储或普通业务表。
