# Basic-Platform 接口文档（当前实现）

> **用途**：提供给后端开发与调用方进行真实接口对接。
> **范围**：路由以 `backend/internal/transport/http/router.go` 为准；请求/响应字段以各模块 `interfaces/http` 适配器为准。
> **生成日期**：2026-07-21。本文不把旧设计稿、前端 mock 或未注册路由写成可调用接口。

## 1. 总体约定

### 1.1 地址、格式与时间

- 控制台业务 API 的公共前缀是 `/api/v1`。
- 登录与 OIDC/OAuth 协议端点位于根路径，例如 `/api/v1/auth/login`、`/oauth2/token`、`/.well-known/openid-configuration`。
- 普通平台 API 使用 JSON；表单协议端点（OAuth/OIDC）使用 `application/x-www-form-urlencoded` 或查询参数，且**不使用**平台统一响应包裹。
- `time.Time` / 时间字符串字段由 Go JSON 编码输出为 RFC 3339 时间；本文不把它缩写成仅日期。

### 1.2 平台统一成功 / 失败响应

除 OAuth/OIDC 协议端点和文件下载外，HTTP 适配器通过以下包裹返回数据：

```json
{
  "code": "OK",
  "message": "操作成功",
  "request_id": "服务端请求 ID",
  "data": {}
}
```

```json
{
  "code": "PLATFORM_VALIDATION_ERROR",
  "message": "请求参数不合法",
  "request_id": "服务端请求 ID",
  "details": {}
}
```

当前共享错误码包括：

| HTTP 状态 | 错误码 | 场景 |
|---:|---|---|
| 401 | `AUTH_UNAUTHENTICATED` | 未登录、会话/JWT 无效或已过期。 |
| 403 | `AUTH_FORBIDDEN` | 已认证但缺少路由要求的权限。 |
| 404 | `PLATFORM_NOT_FOUND` | 路由或资源不可用。 |
| 405 | `PLATFORM_METHOD_NOT_ALLOWED` | 已知路由但方法不支持。 |
| 409 | `IAM_CONFLICT` / `IAM_VERSION_CONFLICT` | 业务状态冲突或乐观锁版本冲突。 |
| 422 | `PLATFORM_VALIDATION_ERROR` | JSON、表单或业务输入校验不通过。 |
| 500 | `PLATFORM_INTERNAL_ERROR` | 服务端已记录内部异常。 |
| 503 | `PLATFORM_DEPENDENCY_UNAVAILABLE` | 就绪检查发现依赖不可用。 |

MFA 二次验证还会使用：`AUTH_MFA_STEP_UP_REQUIRED`（403）、`AUTH_MFA_STEP_UP_EXPIRED`（410）、`AUTH_MFA_VERIFICATION_FAILED`（401）、`AUTH_MFA_ATTEMPTS_EXCEEDED`（401）。

### 1.3 控制台会话、应用 Bearer 与 MFA 二次验证

| 调用边界 | 认证方式 | 适用路由 |
|---|---|---|
| 控制台用户 | `AUTH_SESSION_COOKIE_NAME` 对应的 HttpOnly Cookie；默认配置名为 `bp_session` | 大多数 `/api/v1` 管理接口和 `/api/v1/auth` 的 refresh/logout/me。 |
| 外部应用接入 | `Authorization: Bearer <application access token>` | `POST /api/v1/audit/events` 与 `POST /api/v1/audit/events:batch`。还必须有 `audit.ingest` scope。 |
| 高风险管理操作 | 已登录 Cookie + `X-MFA-Step-Up-Grant: <one-time-grant>` | 路由表中标为“是”的操作。授权与当前 tenant/account/session 绑定，且由中间件消费一次。 |

**不能把浏览器会话 JWT 放进 `Authorization` 请求头替代 Cookie。** 当前 `Authentication` 中间件只读取配置的 session Cookie；应用 Bearer 认证只用于独立接入边界。

### 1.4 通用输入规则

- JSON 适配器普遍使用 `DisallowUnknownFields`，未知字段会导致 422；不要发送客户端私有字段。
- 多数写操作需要 `version` 以实施乐观锁；字段在 DTO 中出现并不表示可省略。
- `tenant_id`、审计人、创建人等不是控制台请求体字段，服务端从认证主体取得。
- 带 `*` 的字段在下面 DTO 目录中对应 Go 指针 / 可空响应值；这说明 JSON 适配器可以区分“未给出 / null”和零值，但最终必填性仍由当前业务用例校验决定。

## 2. 健康、初始化与登录

| 方法与路径 | 认证 / 权限 | 请求体或参数 | 成功数据 / 行为 |
|---|---|---|---|
| `GET /healthz` | 无 | 无 | 存活检查。 |
| `GET /readyz` | 无 | 无 | 就绪检查；依赖不可用时返回 503。 |
| `POST /api/v1/iam/bootstrap/first-super-admin` | Bootstrap Token 按配置启用；配置 token 时限流 5 次/分钟 | `bootstrapRequest` | 创建首次超级管理员；仅初始化状态允许时成功。 |
| `POST /api/v1/auth/login` | 无；30 次/分钟 | `loginRequest` | 无 MFA：200、Set-Cookie、`sessionResponse`；需 MFA：202、`mfaRequiredResponse`，不下发会话 Cookie。 |
| `POST /api/v1/auth/login/mfa:verify` | 无；30 次/分钟 | `verifyMFALoginRequest`；预认证凭据也可由受控 Cookie 解析 | 200、Set-Cookie、`verifyMFALoginResponse`。 |
| `POST /api/v1/auth/token/refresh` | 控制台 Cookie | 无 | 200、替换会话 Cookie、`sessionResponse`。 |
| `POST /api/v1/auth/logout` | 控制台 Cookie | 无 | 撤销当前会话并清除 Cookie。 |
| `GET /api/v1/auth/me` | 控制台 Cookie | 无 | 当前受信任主体：tenant、user、account、roles、permission_codes。 |
| `GET /api/v1/auth/external/login` | 无；30 次/分钟 | 查询参数：`tenant_id`、`provider_code`、`return_to` | 启动已配置外部 **OIDC** 提供商的浏览器授权码登录；服务端设置短期 HttpOnly 浏览器绑定 Cookie 后重定向到上游授权地址。 |
| `GET /api/v1/auth/external/callback` | 无；30 次/分钟 | 查询参数：`state`、`code`；上游失败时可带 `error` | 校验并一次性消费登录状态、浏览器绑定和上游身份；成功时重定向，并设置平台会话 Cookie 或 MFA 前置 Cookie。 |

> 上述 `/external/*` 路由当前实现是外部 **OIDC** 浏览器登录，不是钉钉扫码接口。

### 2.1 钉钉第三方企业应用扫码登录契约

钉钉扫码使用独立 `DINGTALK_QR` 提供商，不是现有 `/auth/external/*` 的 OIDC 兼容分支。只有管理员预先绑定、绑定有效且本地租户、提供商、用户与账号均为启用状态的平台账号可以登录；流程不自动创建用户、账号、任职、角色或权限。

| 项目 | 当前实现契约 |
|---|---|
| 提供商与密钥 | `DINGTALK_QR` 配置在当前管理 HTTP 接口中使用 `client_id`、`client_secret`、`callback_uri` 与 `authorization_scopes`。第三方企业应用（ISV）内嵌二维码场景中，`client_id` 对应钉钉 `SuiteKey`，`client_secret` 对应 `SuiteSecret`/客户端密钥；`app_key`/`app_secret` 仅为兼容性术语，不是当前请求 JSON 字段。`client_secret` 仅可写入，应用层加密保存；读取响应仅以 `client_secret_configured` 表示是否已配置，绝不返回密钥。`OIDC` 仍按其独立字段和校验运行。 |
| 扫码会话 | `POST /api/v1/auth/dingtalk/qr-sessions` 匿名创建短时、一次性会话。请求必须提供 `tenant_id`、`provider_code`、受限同源相对路径 `return_to`；响应 `data` 固定为 `session_id`、`expires_at`、`render_mode: "dingtalk_frame"` 及 `sdk_config:{client_id,redirect_uri,response_type:"code",scope,state,prompt?}`。当前启动装配的 state 时长为 5 分钟。 |
| 创建结果 | 成功为 `201`。输入校验失败为 `422 PLATFORM_VALIDATION_ERROR`；租户或可用钉钉提供商不可用为 `404 AUTH_DINGTALK_PROVIDER_NOT_AVAILABLE`；未分类服务端异常为 `500 PLATFORM_INTERNAL_ERROR`。创建响应和回调均设置 `Cache-Control: no-store`、`Pragma: no-cache`、`Referrer-Policy: no-referrer`。 |
| state 与状态存储 | state 只返回给发起请求的浏览器，位于 `sdk_config.state`；MySQL 表 `iam_dingtalk_qr_login_state` 仅保存 `state_hash` 与加密服务端载荷。原始 state、浏览器绑定值、授权码、上游令牌和原始外部身份标识不得入库、入日志、入审计详情或进入 Cookie。状态按 `ACTIVE`、`CONSUMED`、`EXPIRED` 受控；回调在事务内锁行并消费。 |
| 浏览器绑定 | 创建会话时设置短时 HttpOnly 浏览器绑定 Cookie，固定 `SameSite=Lax`。该 Cookie 不是平台会话 Cookie，且不含 state 或钉钉协议敏感值。通过浏览器绑定校验后 state 会先被一次性消费；绑定不匹配不会消费 state。 |
| 前端二维码 | 登录页固定加载钉钉官方 **DTFrameLogin SDK**，只使用 `sdk_config` 渲染内嵌二维码。SDK 成功后，前端必须先核验回调 state 与 redirect URL，再由顶层页面导航到回调接口；内嵌容器不完成平台会话，也不使用跨窗口消息桥接。 |
| 浏览器回调 | `GET /api/v1/auth/dingtalk/callback` 接收 `state` 与优先使用的 `authCode`；兼容 `code`，但两者同时出现时必须相同。可接收上游 `error`。服务端校验 state 摘要、浏览器绑定、有效期与一次性消费，然后换取并校验钉钉身份，以 `(tenant_id, provider_code, subject_hash)` 查找预绑定身份；仅接受有效绑定及启用的提供商、租户、用户和账号。 |
| 回调响应与错误码 | 回调以 `303 See Other` 完成。普通成功跳转至受限 `return_to` 并沿用 `AUTH_SESSION_COOKIE_*` 写既有会话 Cookie；需要 MFA 时跳转至 `/login?dingtalk_mfa=1&return_to=...` 并仅写既有预认证 Cookie；失败跳转至 `/login?dingtalk_error=<稳定错误码>`。稳定错误码为 `AUTH_DINGTALK_CALLBACK_INVALID`、`AUTH_DINGTALK_QR_SESSION_INVALID`、`AUTH_DINGTALK_IDENTITY_VERIFICATION_FAILED`、`AUTH_DINGTALK_EXTERNAL_IDENTITY_NOT_BOUND`、`AUTH_DINGTALK_PROVIDER_DISABLED`、`PLATFORM_INTERNAL_ERROR`；非 `GET` 请求跳转 `PLATFORM_METHOD_NOT_ALLOWED`。进入回调服务处理、执行 state 校验前会清除扫码浏览器绑定 Cookie；方法、查询长度或授权码冲突等早期拒绝不依赖清除，Cookie 自行短时过期。 |
| 会话与 MFA | 钉钉授权结果、授权码和上游令牌不是平台 JWT。预绑定成功后才复用现有会话签发逻辑：不需要 MFA 时由后端写入平台 HttpOnly 会话 Cookie；需要 MFA 时只写预认证 Cookie，必须完成既有 MFA 登录验证后才创建会话。 |
| 审计与日志 | 会话创建使用 `auth.dingtalk_qr_session.create`；可建立可信 tenant/provider 生命周期上下文的回调使用 `auth.dingtalk_qr_callback`，预绑定成功另记 `auth.dingtalk_qr_binding`。无法建立该上下文的早期拒绝只写安全日志。两类记录均不得包含 state、授权码、SuiteSecret/客户端密钥、上游令牌、原始 `unionId`、浏览器绑定值、平台 JWT 或 MFA 凭据。审计写入失败只记录服务端错误，不阻断登录处理。 |

接口字段、错误码和 Cookie 响应头以 `api/openapi/平台接口规范.yaml` 为唯一机器可读契约；实现流程、前端校验和数据安全要求以《钉钉第三方企业应用扫码登录开发说明》为准。

## 3. OIDC / OAuth 协议端点

这些端点返回 OAuth/OIDC 规范风格的 JSON 或重定向，不使用 `code/message/request_id/data` 包裹。已注册端点如下：

| 方法与路径 | 主要输入 | 主要输出 / 说明 |
|---|---|---|
| `GET /authorize` | 查询参数：`response_type`、`client_id`、`redirect_uri`、`scope`、`state`、`nonce`、`code_challenge`、`code_challenge_method`、`request_uri` 等 | 当前处理 `response_type=code`；成功时按已验证 redirect URI 重定向。 |
| `POST /oauth2/token` | 表单 `grant_type`；支持 `authorization_code`、`refresh_token`、`client_credentials` | 返回 `access_token`、`token_type`、`expires_in`，并可返回 `refresh_token`、`id_token`、`scope`。客户端认证由 Basic 或受支持的表单字段处理。 |
| `POST /oauth2/par` | 表单授权请求 + 客户端认证 | 201：`request_uri`、`expires_in`。默认 PAR TTL 在 handler 中为 90 秒。 |
| `POST /oauth2/revoke` | 表单 `token`、可选 `token_type_hint` + 客户端认证 | 撤销处理；协议错误采用 OAuth error JSON。 |
| `GET /oauth2/consent` | 已认证浏览器会话及同意上下文 | 返回当前同意页面所需数据。 |
| `POST /oauth2/consent/grant` | 与 OIDC issuer 同源；已认证浏览器会话 | 提交授权同意。路由有 Same-Origin 防护。 |
| `DELETE /oauth2/consent` | 已认证浏览器会话 | 撤销用户同意。 |
| `GET /.well-known/openid-configuration` | 无 | OIDC discovery 文档。 |
| `GET /oauth2/jwks` | 无 | 当前 OIDC 签名公钥集合。 |
| `GET` / `POST /oauth2/userinfo` | Bearer access token | 返回 access token 对应用户信息；额外核对当前 client/session/subject 仍有效。 |
| `GET` / `POST /oauth2/logout` | 会话 / 协议参数 | 登出当前 OIDC 会话。 |

### 3.1 Token 与 PAR 的已确认表单约束

- `/oauth2/token` 拒绝 query string；同一表单字段不能重复。支持的 grant 值为 `authorization_code`、`refresh_token`、`client_credentials`。
- authorization-code 交换读取：`code`、`redirect_uri`、`code_verifier`；refresh 读取 `refresh_token`；两者都会走客户端认证。
- client-credentials 支持 `scope` 空格分隔输入；该流程产生应用 access token，详细 JWT 约束见《JWT文档》。
- `/oauth2/par` 仅接受 `response_type=code`；校验 `scope`、`state`（最大 2048）、`nonce`（最大 255）、redirect URI 的绝对性，以及 PKCE `code_challenge` / `code_challenge_method` 的成对出现。支持的方法是 `S256` 或 `plain`。

**`DINGTALK_QR` 提供商配置约束（已由当前应用层校验）**

- 创建时 `type` 必须为 `DINGTALK_QR`；`issuer` 必须为空，因为该扫码交换不属于 OIDC。`OIDC` 与之相反，要求有效 issuer，不能用钉钉配置替代普通 OIDC 配置。
- `client_id` 的业务语义是钉钉 SuiteKey；首次创建的 `client_secret` 是钉钉 SuiteSecret/客户端密钥；`app_key` / `app_secret` 仅为兼容性术语，不是当前 HTTP JSON 字段。更新请求中的 `client_secret` 是可选指针字段：未提供时不表示清除既有密钥。响应只给出 `client_secret_configured` 和 `client_secret_updated_at`，不回传密钥明文或密文。
- `callback_uri` 必须是合法 HTTPS URL。`authorization_scopes` 必须至少有一项、每项非空且不含控制/空白字符；钉钉权限不要求在管理配置中显式填写 OIDC 的 `openid`。钉钉授权地址构造器会在最终向上游发起授权请求时补入 `openid`；这是运行时构造行为，不改变管理接口的输入校验。具体可授予的钉钉权限名称由上游应用配置决定，当前仓库不会枚举或伪造它们。
- 创建外部身份绑定时传入的 `external_subject` 由服务端散列后保存；管理响应中的绑定对象不暴露其原始值。该管理接口本身不构成钉钉扫码回调或身份换取能力。

## 5. 外部系统审计接入接口

| 方法与路径 | 认证与 scope | 请求体 | 成功结果 |
|---|---|---|---|
| `POST /api/v1/audit/events` | `Authorization: Bearer` 应用 access token + `audit.ingest`，以及关联请求头 | `eventInputPayload` | 202；单事件接收回执 `{event_id,status}`。 |
| `POST /api/v1/audit/events:batch` | 同上 | `{ "events": [eventInputPayload] }` | 202；每个事件一个 `{event_id,status}` 回执；同时持久化一条批量投递接收记录。 |

两条外部接入路由均要求以下请求头：

| 请求头 | 要求 |
|---|---|
| `X-Request-ID` | 非空且匹配 `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`；审计接入中间件将其作为可信投递请求标识。 |
| `traceparent` | 采用 4 段 W3C base 格式；trace ID 必须为 32 位小写十六进制，且 trace/parent ID 不能全零。服务端提取其中 trace ID。 |
| `X-Correlation-ID` | 非空且匹配与 `X-Request-ID` 相同的标识规则。 |

单事件请求体中的 `request_id`、`trace_id`、`correlation_id` 必须与上述请求头表达的值一致。批量请求的请求头描述整次投递；每个事件正文仍必须携带自身原始的 `actor_type`、`request_id`、`trace_id`、`correlation_id`，不要求逐项等于投递请求头。

这两条 POST 路由与控制台审计查询使用不同认证中间件：外部系统没有控制台用户角色权限也能接入，但必须有应用 token 和 `audit.ingest` scope；反之，用户 Cookie 不能替代 Bearer token。

## 6. 对接检查清单

1. 控制台调用启用 cookie 凭据，不能自行读取或持久化 JWT。
2. 写接口先读取最新资源并原样提交 `version`；收到 409 后重新读取而不是盲目重试。
3. 高风险路由先完成 step-up challenge，再在**下一次**目标请求携带一次性 `X-MFA-Step-Up-Grant`。
4. OAuth/OIDC 客户端按协议格式处理错误（`error` / OAuth redirect），不要用平台错误包裹解析器处理。
5. 从所有响应记录 `request_id`，用于与服务端结构化日志、审计事件关联。
6. 密码、`client_secret`、MFA secret、恢复码、重置临时密码、step-up grant 都是敏感一次性值：禁止写日志、审计详情、浏览器持久化存储或普通业务表。
